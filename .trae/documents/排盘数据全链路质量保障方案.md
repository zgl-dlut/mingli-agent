# 排盘数据全链路质量保障方案

## 问题背景

用户担心排盘数据在整个链路中的不可控性：
- 排盘算法计算结果可能有误（四柱、旺衰、用神等）
- 数据传递过程可能丢失或错误
- LLM 可能编造与传入数据不符的干支、五行等

## 当前状态分析

### 已有保障机制

1. **数据完整性校验** (`chart_validator.py`)
   - `validate_chart_data()`: 校验 8 个关键字段非空
   - `validate_chart_data_with_values()`: 校验字段值的格式和范围（四柱格式、日主格式、用神/忌神五行、大运/流年干支是否在六十甲子中）
   - `get_chart_fingerprint()`: 提取命盘指纹用于日志审计

2. **LLM 输出检测** (`followup_structured.py`)
   - 已实现 22 个 `_detect_*` 检测函数，覆盖：
     - 干支一致性：流月、大运、流年干支校验
     - 五行一致性：用神五行校验
     - 逻辑一致性：吉凶年方向锁定、用神矛盾检测
     - 内容质量：禁用术语、干支纪时、同义矛盾、维度覆盖、摘要去重
     - 时间线：时间倒挂检测、年份混淆检测、过去月份建议检测
     - 工具调用：缺少工具调用检测
     - 结论依据：关键结论必须有排盘依据

3. **单元测试**
   - `test_paipan_standard_cases.py`: 5 个标准用例（覆盖用户反馈、边界节气、调候用神等）
   - `test_e2e_paipan_to_report.py`: 端到端数据校验和检测函数测试
   - `test_bazi_data_flow.py`: 排盘数据流程测试
   - `test_chart_validator.py`: 数据完整性校验测试
   - `test_liuyue_pipeline.py`: 流月数据链路测试

### 当前风险点

| 环节 | 风险 | 现有保障 | 缺口 |
|------|------|---------|------|
| 排盘算法 | 计算错误（早晚子时、起运年份边界） | 5个标准用例 | 缺少早晚子时修复、起运年份边界修复、用例覆盖不足 |
| 数据传递 | 字段丢失/转换错误 | chart_validator 校验格式/范围 | 已覆盖（基本满足） |
| LLM 输出 | 编造干支/五行 | 22个检测函数 | 已覆盖（较全面） |
| 工具调用 | 未调用工具获取数据 | _detect_missing_tool_calls | 已覆盖 |
| 端到端 | 全链路集成错误 | e2e测试（数据传递+检测函数） | 缺少真实LLM调用测试 |

## 综合保障方案

### 第一层：排盘算法正确性修复（优先级：最高）

**目标**: 修复已知算法问题，确保排盘计算结果与标准排盘工具一致

**问题清单**:

1. **早晚子时问题**（影响约8.3%命盘）
   - 现状：23:00-24:00出生的命盘，日柱未按第二天计算
   - 修复：在 `bazi_service.py` 的日柱计算逻辑中，判断出生时间在23:00-24:00之间时，日柱按次日计算
   - 验证：添加测试用例（如1994-10-13 23:30，日柱应为次日）

2. **大运起运年份边界问题**（影响约5%命盘）
   - 现状：`round()` 四舍五入导致起运年份偏差（如5.5岁→6岁，但传统应按5岁）
   - 修复：改为向下取整（`int()`），符合传统命理"虚岁"计法
   - 验证：添加边界用例（如起运年龄5.5岁、4.3岁等）

3. **调候用神算法优化**（低优先级）
   - 现状：未区分天干阴阳，可能导致用神选择不准
   - 修复：在 `tiaohou_skill.py` 中增加天干阴阳判断
   - 验证：对比标准用例的用神结果

**实现步骤**:

1. 修复早晚子时逻辑
   ```python
   # bazi_service.py - 日柱计算
   if birth_hour == 23:  # 23:00-24:00属于晚子时，日柱按次日
       day_ganzhi = calculate_day_ganzhi(date + timedelta(days=1))
   else:
       day_ganzhi = calculate_day_ganzhi(date)
   ```

2. 修复起运年份计算
   ```python
   # bazi_service.py - 大运起运
   # 改为向下取整，不四舍五入
   start_year = birth_datetime.year + int(start_age)
   ```

3. 扩展标准测试用例库
   - 从当前5个扩展到15-20个
   - 覆盖：早晚子时、立春前后、节气交接、起运边界、特殊格局等

## 风险与缓解

| 风险 | 缓解措施 |
|------|---------|
| 早晚子时修复影响已有数据 | 先备份数据，修复后对比验证 |
| 起运年份修复影响大运计算 | 添加边界测试用例，确保修复正确 |
| 检测规则误杀 | 宽松模式 + 人工审核 |
| 测试覆盖不全 | 定期回顾，补充用例 |
| 性能影响 | 检测函数异步执行，不阻塞主流程 |
| 真实LLM测试成本高 | 仅在CI/CD中定期运行，不每次部署都运行 |

## 总结

要保证排盘数据在整个链路中没有错误，需要多层保障：

1. **源头保障**：修复排盘算法的已知问题（早晚子时、起运年份边界），确保计算结果正确
2. **传递保障**：在关键节点添加数据校验，确保数据不丢失、不变形
3. **输出保障**：利用已有的22个检测函数，确保LLM输出与传入数据一致
4. **集成保障**：通过端到端测试，验证整个链路的正确性
5. **监控保障**：在生产环境中监控质量指标，及时发现问题

当前最紧迫的是修复排盘算法的已知问题（早晚子时、起运年份边界），这是源头问题，影响面最广。其次是完善数据传递校验和端到端测试，形成完整的质量保障体系。
