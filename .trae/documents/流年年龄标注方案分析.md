# 流年年龄标注 vs 出生年份 — 方案分析

## Summary

用户质疑：在重点流年数据中标注年龄是否有必要？流年数据不全（只有5个重点流年），如果依靠流年标注年龄，数据缺失时会导致计算错误吗？

**结论：两者都保留，互为补充。流年标注年龄是"锚点"，出生年份是"基准"。但需要补一条 prompt 规则，明确要求 LLM 涉及年龄时以 prompt 提供的数据为准，禁止自行推算。**

## Current State Analysis

### 已实现的改动（上一轮）
1. **流年标注年龄**（已实现）：`_format_key_liunian` 函数新增 `birth_year` 参数，每个流年后标注年龄如 `2034年 甲寅：大吉（...），8岁`
2. **prompt 增加出生年份**（已实现）：`年龄：0岁（2026年出生），儿童期（0-12岁）`

### 用户的担忧（合理）
- 重点流年只有 5 个，其他年份没有年龄标注 → LLM 仍需自己算
- 重点流年数据可能为空（[orchestrator.py:344](file:///Users/zhangguangling/Downloads/命理推算/mingli-agent/backend/app/skills/orchestrator.py#L344) 初始化为 `[]`，大运流年模块导入失败时保持空）→ 流年标注完全失效
- 如果 LLM 依赖流年标注，数据缺失时反而出错

### 两种方案的优劣

| 方案 | 优点 | 缺点 |
|---|---|---|
| **仅出生年份** | 通用，覆盖所有年份；流年数据缺失时仍有效 | LLM 数学计算不可靠（这次 8 岁算成 18 岁就是例子） |
| **仅流年标注** | 重点流年直接读年龄，无需计算 | 只覆盖 5 个年份；流年数据为空时完全失效 |
| **两者都做（当前）** | 双重保障：重点流年有锚点，其他年份有出生年份 | 需确保两者一致（代码中都用同一个 birth_year 计算，不会不一致） |

### 关键事实
- **两者数据源相同**：流年标注的年龄 = `ly['year'] - birth_year`，prompt 中的出生年份也是同一个 `birth_year`。不可能不一致。
- **流年标注不影响出生年份**：即使流年数据为空，prompt 中的"2026年出生"仍然存在，LLM 仍可参考。
- **LLM 数学能力不可靠是根因**：即使给了出生年份"2026年出生"，LLM 推算"2034年几岁"时仍可能算错。流年标注的价值在于：对 LLM 最常引用的 5 个年份，直接给出正确答案。

## Proposed Changes

### 改动：在 prompt 规则中增加年龄使用约束

**文件**：`backend/app/services/followup_structured.py`

**位置**：prompt 模板中的"命盘权威与方向锁定"规则区域（约 line 200-270 之间的规则列表）

**做什么**：在规则中增加一条年龄使用约束：

```
- 涉及流年年龄时，必须以命盘数据中标注的年龄或出生年份为准，禁止自行推算
  （如命盘标注"2034年，8岁"，不得写成"18岁"）
```

**为什么**：当前虽然给了流年标注年龄和出生年份，但 LLM 仍可能"自信地"自行计算。加一条规则约束，配合已有的数据标注，形成"数据+规则"双重保障。

### 不需要改动的部分
- **流年标注年龄**：保留，不删除。它是重点流年的"锚点"，有数据时帮助校准，无数据时不影响（因为出生年份仍在）。
- **prompt 中的出生年份**：保留，不删除。它是通用基准，覆盖所有年份。

## Assumptions & Decisions

1. **两者保留的决定依据**：流年标注年龄和出生年份数据源相同（同一个 birth_year），不会不一致。流年标注是"加分项"而非"必需项"，数据缺失时降级为仅靠出生年份，不会出错。

2. **不删除流年标注的理由**：删除后，LLM 在涉及重点流年时完全靠自己计算年龄，而 LLM 数学能力不可靠（已有实证：8 岁算成 18 岁）。保留标注至少保证最常引用的 5 个年份是正确的。

3. **加规则约束的必要性**：即使有了数据标注，LLM 仍可能"忽略"标注而自行计算。规则约束是第三层保障，从 prompt 层面要求 LLM 以数据为准。

4. **不增加代码层年龄校验**：原因是在 followup_structured.py 的自检规则中增加年龄校验需要解析 LLM 输出中的年龄数字并对比，实现复杂且误判率高（如"8岁"vs"八岁"vs"8周岁"）。prompt 规则约束已足够。
