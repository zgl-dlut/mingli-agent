# 上下文缓存方案对比分析

## Summary

**是的，隐式缓存是模型默认支持的形式，无需任何配置，无法关闭。** 但实测发现隐式缓存在我们的 prompt 结构下命中率极低（cached=0），原因是固定规则段和动态命盘数据混在同一个 system message 中，prefix 每次都不同。直接用隐式缓存不可行，需要调整 messages 结构让固定部分成为真正的公共前缀。

## Current State Analysis

### 两种缓存模式对比

| 项目 | 显式缓存 | 隐式缓存 |
|---|---|---|
| 是否需要配置 | 需在 messages 加 cache_control 标记 | **无需配置，默认开启，无法关闭** |
| 最少 Token | 1024 | 256 |
| 有效期 | 5分钟（命中后重置） | 不确定，系统定期清理 |
| 命中率 | 确定性命中 | **不确定**，依赖公共前缀匹配 |
| 命中计费 | 输入价 10% | 输入价 20% |
| 互斥性 | **两者互斥，单个请求只能用一种** | 同左 |

### 实测结果

**显式缓存（cache_control 标记）**：
- 单个 content block + cache_control → ✅ 缓存命中（cached=1042）
- 两个 content block（固定段加标记+动态段不加）→ ❌ 未命中
- 追问链路（build_cache_control_messages 拆分两个 block）→ ❌ cached=0

**隐式缓存（无标记，依赖公共前缀）**：
- 追问链路（system_prompt 混合固定+动态内容）→ ❌ cached=0
- 原因：固定规则段和动态命盘数据在同一个 system message 中，每次追问 prefix 都不同

### 根因分析

当前 system_prompt 结构：
```
[固定规则段 8000+ tokens] + [动态命盘数据 3000+ tokens]
```
- 显式缓存尝试在固定段末尾加 cache_control 标记拆分两个 block，但实测**两个 block 结构未命中**（原因待查，可能是阿里云对多 block cache_control 的支持有限制）
- 隐式缓存要求**从头开始的公共前缀**完全相同，但当前结构中动态部分混在 system message 里，前缀每次都变

## Proposed Changes

### 方案：拆分 system message 为两个 message，利用隐式缓存

**核心思路**：把一个 system message 拆成两个 system message——第一个是固定规则（每次相同），第二个是动态命盘数据（每次不同）。隐式缓存会自动缓存第一个 system message 的公共前缀。

**文件**：`backend/app/services/ai_service.py` - `build_cache_control_messages` 函数

**改动**：
```python
def build_cache_control_messages(system_prompt: str, user_messages: list) -> list:
    SPLIT_MARKER = "# 本次会话信息"
    split_idx = system_prompt.find(SPLIT_MARKER)

    if split_idx > 0:
        fixed_part = system_prompt[:split_idx].rstrip()
        dynamic_part = system_prompt[split_idx:]
        # 拆成两个 system message，而非一个 system message 两个 content block
        return [
            {"role": "system", "content": fixed_part},  # 固定规则，每次相同
            {"role": "system", "content": dynamic_part},  # 动态命盘数据
        ] + user_messages
    else:
        return [{"role": "system", "content": system_prompt}] + user_messages
```

**为什么这样可行**：
- 隐式缓存识别**请求的公共前缀**，第一个 system message（固定规则）每次完全相同
- 第二个 system message（动态命盘数据）不同，但不影响第一个 message 的缓存
- 无需 cache_control 标记，纯靠隐式缓存的公共前缀匹配
- 函数名保留不变（避免改动调用方），但语义从"显式缓存标记"变为"结构拆分以利用隐式缓存"

**同时移除**：cache_control 标记（因为显式和隐式互斥，加了显式标记反而阻止隐式缓存工作）

## Assumptions & Decisions

1. **移除 cache_control 标记**：显式和隐式互斥。当前显式缓存在两 block 结构下不工作，移除标记让隐式缓存接管。

2. **拆成两个 system message 而非两个 content block**：实测单 block 显式缓存可行但两 block 不可行。两 system message 结构让隐式缓存能识别固定前缀。

3. **不改动 build_structured_prompt**：prompt 模板不变，只在 build_cache_control_messages 中拆分。

4. **保留函数名 build_cache_control_messages**：避免改动 3 处调用方（followup_structured.py + ai_service.py）。函数注释更新为说明隐式缓存策略。

## Verification Steps

1. 修改 build_cache_control_messages：拆成两个 system message，移除 cache_control 标记
2. 重启 uvicorn（.env 已改公共 endpoint，需重启生效）
3. 对同一人物触发两次追问（5分钟内）
4. 检查日志：第二次 cached_tokens 应 > 0
5. 如果仍为 0，说明隐式缓存也不工作，需进一步排查
