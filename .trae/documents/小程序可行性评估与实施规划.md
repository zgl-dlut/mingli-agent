# 小程序可行性评估与实施规划

> 整理日期：2026-09-14
> 背景：趣算算当前为认证服务号 H5（https://www.qusuansuan.com/，React 18 + Vite，FastAPI 后端），评估迁移/新增微信小程序端的可行性、工作量与风险，并纳入语音输入方案选型。

---

## 一、结论速览

- **后端基本零改动复用**：排盘、AI 报告、追问、积分、账户、订单等 Python 核心逻辑直接共用，仅需新增小程序登录、小程序虚拟支付两套外围链路。
- **前端需用 Taro 重写 8 个用户页面**，预估 **4–6 周**；管理后台不搬。
- **最大风险是小程序审核**：微信官方明确**占卜/算命类目不开放**（2025-11 官方回复），产品必须以「传统文化趣味解读 + AI 工具」形态过审，共排查出 **18 项合规问题**（见第六章），其中 **8 项 P0 不做必驳**。
- **AI 资质是硬门槛**：AI 问答必须开通「深度合成-AI 问答」类目（**仅企业主体**），需提供大模型厂商（阿里通义）的算法备案 + 合作协议，并在报告页显著标注「AI 生成」。
- **支付必须重做**：积分属虚拟商品，2026-04 起强制走小程序虚拟支付（安卓费率 1%、**iOS 苹果抽成 12%**），禁止跳转 H5 充值。
- **备选方案 web-view 套壳价值有限**：2–3 天可上线，但同样受类目审核，且 H5 充值/分享奖励在小程序 web-view 内依然违规，只能做纯免费体验壳。
- **语音是小程序的明显加分项**：小程序官方「同声传译」插件**免费支持边说边出字**（实时识别），H5 免费接口做不到。

## 二、后端复用评估

### 可直接复用（零改动）

- 八字排盘、真太阳时、农历转换
- AI 首次报告、追问（含 prompt、编造检测、评测链路）
- 积分体系（扣费、充值、新用户赠送、白名单；分享奖励仅 H5 保留，见 P0-6）
- 人物管理、会话与消息存储
- 时间线/择日等后续 Agent 能力

### 需新增或改造（共 3 项）

1. **小程序登录**
   - 新增 `code2session` 登录分支，用 `js_code` 换 openid/session_key。
   - `users` 表已有 `wechat_openid` 字段，直接落库；同一主体下可用 **unionid 与公众号 H5 账号打通**，积分余额天然共享。

2. **小程序虚拟支付（全新链路，非简单分支）**
   - 现有 JSAPI 支付仅服务 H5（公众号 openid）；积分属虚拟商品，小程序端必须走官方虚拟支付 `wx.requestVirtualPayment` + 道具发货回调（安卓 1%、iOS 苹果 IAP 12%），需新建下单/回调/对账逻辑；支付成功后的订单与积分入账可复用现有 transactions 体系。详见 P0-5。

3. **流式输出 SSE → 轮询**
   - 小程序不支持 EventSource，一期改用轮询。
   - 现成基础：`generating-status` 接口已存在，H5 断线对账机制已验证「以消息末尾是否为 assistant 作为完成判据」，轮询版直接沿用同一判据。

### 无需改动

- 管理后台全部接口、评测中心、监控采样等。

## 四、风险与备选

### 最大风险：类目审核（封建迷信）

- 微信官方 2025-11 明确答复**占卜类目不开放**，原样提交必驳；且叠加 2026 年 AI 深度合成资质、虚拟支付两项新规，合规门槛比早期同类产品更高。
- **全部 18 项风险与逐条整改方案见第六章**（8 项 P0 不做必驳）。核心思路：定位转为「传统文化趣味解读 + AI 工具」、企业主体 + 深度合成类目、支付/分享/登录/注销按平台规范重做。
- **建议在投入 4–6 周重写前，先走第 0 步合规闸门（类目客服预审 + 阿里备案协议），再决定全量投入。**

### 备选：web-view 套壳（2–3 天）

- 小程序内用 web-view 直接加载现有 H5，改动极小。
- 局限：web-view 同样受类目限制且仍需 AI 资质；**小程序虚拟支付、同声传译插件等原生能力在 web-view 内不可用**，H5 充值与分享奖励在 web-view 场景同样违规，语音仍退回 H5 的「说完再转」。
- 定位：仅能作为**纯免费体验壳**做类目试水（详见 6.4），不承载付费闭环，不是终态。

## 五、语音输入方案对比（重点）

### 三种路线能力边界

| 维度 | ① H5 现状：公众号 JS-SDK | ② 小程序：同声传译插件 | ③ H5 接云 ASR |
|---|---|---|---|
| 识别方式 | 录完整段后一次性翻译 | **边说边返回中间结果** | 边录边推流，实时返回 |
| 实时出字（输入法效果） | ❌ 做不到（官方无实时回调） | ✅ 原生支持 | ✅ |
| 成本 | 免费 | **免费** | 按量付费（约几元/千次） |
| 自家服务器 | 仅签名（已上线） | **不经过，无 ASR 成本** | 需新增临时签名接口 |
| 单次时长 | 60 秒 | 单会话有时长上限，可分段续接（以官方文档为准） | 按流，自行控制 |
| 兼容性 | 微信浏览器，iOS 手势栈已适配 | 小程序内稳定 | **iOS 微信 webview 音频采集兼容风险高** |
| 方言 | — | 普通话、英语、粤语、四川话 | 取决于云厂商 |

### 结论

- **H5 维持现状**：微信给网页的免费录音接口只有「说完再转」，没有实时回调，这是能力边界、非代码问题；不值得为它单独上云 ASR（付费 + iOS 兼容风险）。
- **实时语音放进小程序一期**：免费、稳定、零服务器成本，是小程序相对 H5 的差异化体验亮点。

### 小程序语音技术方案（一期）

- 插件：**微信同声传译 WechatSI**，provider appid `wx069ba97219f66d99`，在小程序管理后台添加后于 `app.json` 声明。
- 核心 API：

```js
const plugin = requirePlugin('WechatSI')
const manager = plugin.getRecordRecognitionManager()

manager.onRecognize = (res) => {
  // res.result：实时中间结果 → 直接回填输入框（即"边说边出字"）
}
manager.onStop = (res) => {
  // res.result：最终结果
}
manager.start({ lang: 'zh_CN' }) // 支持 zh_CN / en_US / zh_HK / sichuanhua
manager.stop()
```

- 需申请录音权限 `scope.record`（首次使用弹窗授权）。
- 交互直接复刻现有 H5 的「微信输入法式」点击 toggle：点话筒开始（文字实时上屏）、再点结束，结果回填输入框可编辑后发送；连续多段自动空格拼接的逻辑保留。
- 识别音频不经过项目服务器，后端无需新增任何语音相关接口。
- 长语音应对：到达单会话时长上限时自动 stop + start 续接，结果继续追加。

## 六、合规风险与整改方案（对照现状逐条排查）

> 排查日期：2026-09-14。依据：《微信小程序平台运营规范》、微信开放社区官方答复（2025-11 占卜类目、2026-04 虚拟支付新规）、《生成式人工智能服务管理暂行办法》、《人工智能生成合成内容标识办法》（2025-09-01 施行）、《个人信息保护法》。
> 分级：**P0 = 不做必驳/违法，上架前置**；P1 = 高频驳回或合规经营必备；P2 = 经营优化/顺带修复。

### 6.1 P0 上架前置项（8 项）

#### P0-1 算命/占卜类目不开放，产品形态必须重新包装
- **现状**：产品核心即八字排盘 + 大运流年吉凶 + 付费解读，原样提审 100% 被驳。微信官方 2025-11 明确答复：「暂未开放占卜类目，涉及算卦占卜、封建迷信属未允许范畴，需移除相关功能后重新提交」。
- **方案**：
  1. 定位转型为「**传统文化趣味解读 + AI 自我探索工具**」：强调八字是传统历法文化、报告是 AI 基于传统文化视角的趣味参考，不是预测、不指导决策。
  2. 目标服务类目：主类目咨询「**文化-传统文化**」或「**生活服务-休闲娱乐**」，同时必须加挂「**深度合成-AI 问答**」类目（见 P0-3）；**不选占卜/算命相关任何类目**。
  3. 提审前在【小程序后台-类目-联系人工客服】提交完整交互 demo 图预审，拿到类目可行性口头/工单确认再投入开发——这是第 0 步闸门。
  4. 审核版本只保留自助解读，**不做**真人算命师、法事、开运物等任何线下迷信延伸。
- **适用端**：小程序（H5 在公众号生态暂可维持，但同样受《互联网信息服务管理办法》第 15 条约束，措辞软化建议同步）。

#### P0-2 平台文案「自述封建迷信」
- **现状**：[legal.py](file:///Users/zhangguangling/Downloads/%E5%91%BD%E7%90%86%E6%8E%A8%E7%AE%97/mingli-agent/backend/app/api/legal.py) 2.1 条写明「提供命理推算、八字分析、占星解读、**运势预测**等服务」；[index.html](file:///Users/zhangguangling/Downloads/%E5%91%BD%E7%90%86%E6%8E%A8%E7%AE%97/mingli-agent/frontend/index.html#L10-L11) title 为「趣算算‑八字大运流年推演平台」。审核员看到即定性。
- **方案**：统一改为「基于传统干支历法文化的 AI 趣味解读工具」；全站（小程序名、简介、logo 文案、页面标题、空状态、分享卡片）禁用：算命、占卜、运势预测、改命、消灾、转运、开光、化解灾煞、精准预测未来等词；现有 7.1 条「不具有预测、占卜、决策功能」的免责底子保留并前移。
- **适用端**：两端通用，H5 协议可一起改版。

#### P0-3 「深度合成-AI 问答」类目资质（周期最长，最先启动）
- **现状**：报告全部由大模型生成，无任何 AI 类目资质。
- **要求**：仅**企业主体**可申请；调用第三方大模型需提交：① 技术主体（阿里通义/百炼）的《互联网信息服务算法备案》（类型须为生成合成类/深度合成）编号截图；② **我方与阿里的合作协议**，协议中须含算法名称/应用场景/备案编号。
- **方案**：
  1. 确认小程序注册主体为企业（营业执照经营范围含文化咨询/信息技术服务类更佳）；
  2. 立即向阿里云客户经理索取通义模型的**算法备案编号与资质材料包**，并签署/补签含备案编号的合作协议（商务流程可能数周，是关键路径）；
  3. 提审时挂「深度合成-AI 问答」类目。
- **适用端**：小程序（H5 侧《暂行办法》同样要求备案，靠调用已备案的通义模型 + 自身服务合规，后续可评估自有服务备案）。

#### P0-4 AI 生成内容显著标识
- **现状**：[Chat.tsx](file:///Users/zhangguangling/Downloads/%E5%91%BD%E7%90%86%E6%8E%A8%E7%AE%97/mingli-agent/frontend/src/pages/Chat.tsx#L1618-L1621) 仅输入框上方一行 10px 浅色免责，**每份报告上没有「AI 生成」标识**。《人工智能生成合成内容标识办法》2025-09 已施行，微信驳回高频项。
- **方案**：每条 AI 回答气泡顶部加显著「AI 生成」角标；报告加载/导出场景同样带标识；现有「AI 存在幻觉，仅供传统文化体验与娱乐参考」保留。
- **适用端**：两端通用（法规要求，非小程序独有）。

#### P0-5 虚拟支付改造（积分 = 虚拟商品）
- **现状**：[RechargePage.tsx](file:///Users/zhangguangling/Downloads/%E5%91%BD%E7%90%86%E6%8E%A8%E7%AE%97/mingli-agent/frontend/src/pages/RechargePage.tsx#L10-L15) 1 元=10 积分、积分兑换报告，是标准虚拟商品；现走 JSAPI 普通商户号。
- **要求**：2026-04-01 起虚拟商品必须全终端接入官方虚拟支付 `wx.requestVirtualPayment`（安卓技术服务费 1%，**iOS 走苹果 IAP 抽成 12%**）；**严禁**在 iOS 展示任何购买按钮/页面后引导去 H5、公众号、扫码支付（运营规范 5.13，绕过即封）。
- **方案**：
  1. 小程序后台开通「虚拟支付」，创建积分包道具（160/200/400… 各档位对应道具 ID），发布道具；
  2. 后端新增小程序虚拟支付下单 + 发货回调分支（代币/道具模式），不复用 JSAPI 链路；
  3. iOS 端开通苹果 IAP 并配置小程序简称；不做任何「去安卓/公众号充值」引导；
  4. 类目须落在虚拟支付开放范围（文娱/工具/深度合成等），**P0-1 类目确认时一并向客服核实虚拟支付资格**。
- **适用端**：小程序。

#### P0-6 分享赚积分 = 利益诱导分享，小程序端必须下线
- **现状**：[ShareModal.tsx](file:///Users/zhangguangling/Downloads/%E5%91%BD%E7%90%86%E6%8E%A8%E7%AE%97/mingli-agent/frontend/src/components/ShareModal.tsx) 明示「邀请 1 位好友=80 积分、多邀多得」，注册时 [auth.py](file:///Users/zhangguangling/Downloads/%E5%91%BD%E7%90%86%E6%8E%A8%E7%AE%97/mingli-agent/backend/app/api/auth.py) 按 ref 自动发奖（share_reward）。运营规范 5.1 零容忍，「积分」被明确列为利益，且官方已点名「好友注册双方得积分」类玩法。
- **方案**：
  1. 小程序端：分享按钮变为**纯自发功能**（分享报告/小程序卡片），删除 ShareModal 奖励文案、ref 发奖入口与「多邀多得」；新人 240 积分保留但**与邀请关系彻底解耦**（任何渠道注册都送，不展示邀请人）；
  2. 后端按端（小程序 appid 来源）关闭 share_reward 发奖；H5 端维持现状（公众号网页不受小程序运营规范管辖），两套裂变策略分离。
- **适用端**：小程序必改；H5 暂保留。

#### P0-7 强制登录才能用，驳回第一名
- **现状**：[App.tsx](file:///Users/zhangguangling/Downloads/%E5%91%BD%E7%90%86%E6%8E%A8%E7%AE%97/mingli-agent/frontend/src/App.tsx#L113-L127) 首页 `/` 被 ProtectedRoute 包裹，未登录直接跳 /login。
- **方案**：小程序首页游客可浏览（产品介绍 + 1 份脱敏**样例报告**体验）；在「创建人物 / 发起解读 / 充值」时才唤起 wx.login 授权登录。路由守卫从「进首页」后移到「关键动作」。
- **适用端**：小程序（重写时直接按此设计）。

#### P0-8 账号注销功能缺失（H5 同样违法）
- **现状**：隐私协议 5.4 条承诺「可随时申请注销」，但全代码库**无注销入口、无注销接口**，仅有协议文本。个保法及小程序审核均要求提供便捷注销，15 个工作日内完成删除或匿名化。
- **方案**：
  1. 后端新增注销接口：二次确认（短信/验证码）→ 解除绑定 → 对 users、persons、bazi_data、chat_sessions、chat_messages、transactions（交易记录按法规保留期限匿名化留存）分级删除/匿名化；
  2. 前端「我的-设置」放注销入口与后果告知；
  3. **H5 与小程序同期补齐**（这是现行 H5 已存在的法律缺陷，不因做小程序才修）。
- **适用端**：两端通用。

### 6.2 P1 高频驳回与经营合规项（6 项）

| # | 问题 | 现状 | 整改方案 | 适用端 |

### 6.4 web-view 套壳的合规再评估

- web-view 加载 H5 **同样要过类目审核**（P0-1/2/3 一条躲不掉，AI 资质仍需提供）；
- web-view 内**不能使用小程序虚拟支付**，H5 JSAPI 充值在 iOS 小程序 web-view 里属违规（P0-5 适用）；
- H5 的分享积分奖励在小程序场景同样会被判诱导（P0-6 适用）。
- 结论：套壳只能作为「**纯免费体验版**」（免费样例 + 传统文化内容展示）用于类目试水，验证不了付费闭环；第二章「2–3 天过渡」的判断维持，但不承载商业化。
