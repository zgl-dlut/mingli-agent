# 评测系统问题修复计划

## 问题清单与根因分析

### 问题 1：narrative 过短检测显示"最少30字"
**根因**：代码已改为 5（structure_checker.py 第 146 行），但数据库中存储的是旧记录。前端展示的是数据库中的历史 violation detail 文本。
**结论**：历史数据问题，新报告会用新阈值 5 字。无需改代码。

### 问题 2：预期违规和实际违规不一致也显示"检测通过"
**根因**：当前 match 逻辑只判断 `actual_pass == expected_pass`（整体通过/失败是否一致），不检查具体违规项是否匹配。
- eval_002 预期违规：`["子问题漏答", "block数量异常"]`
- 实际违规：`["子问题漏答", "block数量异常", "narrative过短"]`
- 两者都 failed → match=true → 显示"检测通过"

**用户期望**：实际检测出的违规项应该和预期违规项逐项对比，多出来的也要标注清楚。

### 问题 3：没有真实数据被检测（只有实验室数据）
**根因确认**：chat.py 第 381-403 行和 643-675 行的调用链路是完整的，但 `save_monitor_result` **只在 `should_deep_eval` 返回 True 时才被调用**。

`should_deep_eval` 的触发条件：
1. 敏感话题（健康/法律/投资/心理）→ 大部分追问不涉及
2. 负面情绪 → 大部分追问不涉及
3. 首次报告 → 只有首次报告触发
4. 规则违规（术语黑名单）→ 修复后很少触发
5. 轻量指标异常（字数<300/block<1/生成<3s/>600s）→ 正常报告不触发
6. 随机 5% → 概率很低

**结论**：大部分正常报告不满足任何触发条件，所以没有 `production_monitor` 记录被保存。

### 问题 4：评测概览页 L1-L4 分不清
**根因**：EvalMethodology 组件中指标卡片没有标注 L1-L4 层级标签。

### 问题 5：评测类型只有"报告质量检测"
**根因**：同问题 3，`production_monitor` 类型数据没有被保存。

## 修改方案

### 修改 1：所有报告都保存轻量监控记录（解决无真实数据问题）

**文件**：`backend/app/api/chat.py`

**改动**：在追问报告（第 379-405 行）和首次报告（第 641-677 行）的生产监控代码块中，即使 `should_deep_eval` 返回 False，也保存一条轻量监控记录。

当前代码：
```python
need_eval, trigger_reason = should_deep_eval(...)
if need_eval:
    await save_monitor_result(...)
```

改为：
```python
need_eval, trigger_reason = should_deep_eval(...)
await save_monitor_result(
    report=report_data,
    user_question=question,
    user_id=user_id,
    session_id=session_id,
    trigger_reason=trigger_reason if need_eval else "no_trigger",
    is_first_report=False,
    generation_time=gen_time,
    chart_data=bazi_data,
)
```

**文件**：`backend/app/services/eval/production_monitor.py`

**改动**：`save_monitor_result` 函数中，当 `trigger_reason == "no_trigger"` 时，不执行 LLM 深度评测（`run_deep_eval`），只保存第一层+第二层的轻量结果。

当前代码（第 316-319 行）：
```python
if eval_detail is None and chart_data:
    eval_detail = await run_deep_eval(...)
```

改为：
```python
if eval_detail is None and chart_data and trigger_reason != "no_trigger":
    eval_detail = await run_deep_eval(...)
```

这样所有报告都会有一条 `production_monitor` 记录，但只有被采样的报告才会触发 LLM 深度评测。

### 修改 2：评测详情页增加违规项逐项对比

**文件**：`frontend/src/pages/EvalDetailPage.tsx`

**改动**：在"预期应检测到的违规项"区域，增加逐项对比逻辑：
- 预期违规项 ∩ 实际违规项 → 标记为"✓ 已检测到"（绿色）
- 预期违规项 - 实际违规项 → 标记为"✗ 未检测到"（红色）
- 实际违规项 - 预期违规项 → 标记为"⚠ 额外检测到"（黄色）

### 修改 3：评测概览页指标卡片标注 L1-L4

**文件**：`frontend/src/components/EvalMethodology.tsx`

**改动**：在"最新版本指标"区域的 5 个指标卡片上增加 L1-L4 标签：
- 检测准确率 → 无层级标签（综合指标）
- 通过率 → L1 技术完成率
- L2 格式 → L2 格式完成率
- 任务完成率 → L3 质量完成率
- 正确率 → L4 综合正确率

同时更新三层检测体系说明卡片中的指标对应关系。

### 修改 4：评测结果页表格按时间倒序 + 增加数据来源筛选

**文件**：`frontend/src/pages/EvalDashboard.tsx`

**改动**：
- 确认表格已按 `created_at` 倒序排列（后端 API 已实现）
- 确认数据来源筛选（全部/实验室/生产）已实现
- 确认所有 eval_type 在筛选下拉框中
