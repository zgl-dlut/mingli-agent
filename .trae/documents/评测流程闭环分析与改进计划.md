# 评测流程闭环分析与改进计划

## 一、当前评测系统架构分析

### 1.1 评测体系概览

系统目前包含**两套独立的评测机制**：

| 评测类型 | 触发时机 | 评测对象 | 数据存储 |
|---------|---------|---------|---------|
| **实验室评测** | 手动运行 `run_batch_eval()` | `eval_dataset.json` 中的预设用例 | `eval_results` 表 (eval_type: report_quality/chart_accuracy/badcase_eval) |
| **生产监控** | 每次报告生成后自动触发 | 真实用户报告 | `eval_results` 表 (eval_type: production_monitor) |

### 1.2 四层评测指标体系 (L1-L4)

```
┌─────────────────────────────────────────────────────────────┐
│  L1 技术完成  │  JSON解析 + Pydantic Schema校验通过           │
├─────────────────────────────────────────────────────────────┤
│  L2 格式完成  │  结构检查 + 叙事检查 + 命盘使用检查（代码层）   │
├─────────────────────────────────────────────────────────────┤
│  L3 质量完成  │  硬性检查全部通过（无术语违规/编造等）          │
├─────────────────────────────────────────────────────────────┤
│  L4 综合完成  │  L1 × L2 × L3 全部通过                       │
└─────────────────────────────────────────────────────────────┘
         ↓ （硬性检查通过后）
┌─────────────────────────────────────────────────────────────┐
│  LLM 软性评分  │  叙事性/通顺性/故事性/加粗合理性/术语通俗化    │
├─────────────────────────────────────────────────────────────┤
│  编造检测      │  LLM 判断是否编造命盘未提供的信息              │
└─────────────────────────────────────────────────────────────┘
```

## 二、问题解答

### 问题1：为什么有些生产数据没有LLM评测？

**答案：这是设计如此，不是Bug。**

系统采用**智能采样策略**（见 `production_monitor.py` 第 142-200 行），只有满足以下条件时才触发LLM深度评测：

| 触发条件 | 触发率 | 原因 |
|---------|-------|------|
| 敏感话题（健康/法律/投资） | 100% | 高风险内容必须检查 |
| 负面情绪（焦虑/绝望等） | 100% | 心理安全考量 |
| 首次报告 | 100% | 第一印象很重要 |
| 规则违规（术语黑名单等） | 100% | 发现已知问题 |
| 轻量指标异常（字数过少/生成过快等） | 100% | 质量异常信号 |
| 随机采样 | 5% | 发现未知问题 |

**未触发的报告**：`trigger_reason = "no_trigger"`，只记录基础监控数据（字数、耗时等），不执行LLM评测，**节省API成本**。

**代码位置**：
- 采样决策：[should_deep_eval()](file:///Users/zhangguangling/Downloads/命理推算/mingli-agent/backend/app/services/eval/production_monitor.py#L142-L200)
- 调用位置：[chat.py#L409](file:///Users/zhangguangling/Downloads/命理推算/mingli-agent/backend/app/api/chat.py#L409)（追问）、[chat.py#L690](file:///Users/zhangguangling/Downloads/命理推算/mingli-agent/backend/app/api/chat.py#L690)（首次报告）

### 问题2：评测未通过后，如何调整？

**当前状态：缺少闭环机制。**

目前系统只做了**检测和记录**，但没有自动化的改进流程。需要人工：
1. 在管理后台「生产监控」Tab 查看未通过的报告
2. 分析违规类型（结构/叙事/命盘使用）
3. 手动决定是调整 prompt、修复代码、还是更新评测规则

**这是需要改进的地方。**

### 问题3：标准评测流程应该如何设计？

**建议的完整闭环流程：**

```
┌─────────────────────────────────────────────────────────────────────┐
│                         评测闭环流程                                  │
├─────────────────────────────────────────────────────────────────────┤
│                                                                     │
│  ┌──────────┐    ┌──────────┐    ┌──────────┐    ┌──────────┐      │
│  │ 1.检测    │ →  │ 2.分类    │ →  │ 3.归因    │ →  │ 4.改进    │      │
│  └──────────┘    └──────────┘    └──────────┘    └──────────┘      │
│       ↑                                                   │         │
│       └───────────────────────────────────────────────────┘         │
│                         5.验证                                       │
│                                                                     │
└─────────────────────────────────────────────────────────────────────┘
```

#### 阶段1：检测（已实现）
- 代码层检查（L1/L2/L3）
- LLM 软性评分
- 编造检测

#### 阶段2：分类（已实现，需增强）
当前按违规类型分类：
- `structure`：结构问题（子问题漏答、block数量异常等）
- `narrative`：叙事问题（术语违规、编造等）
- `chart_usage`：命盘使用问题（用神/忌神不一致等）

**需增强**：增加「可操作」的细分标签
- `prompt_issue`：LLM 理解/执行问题 → 调整 prompt
- `code_bug`：代码逻辑错误 → 修复代码
- `rule_too_strict`：评测规则过严 → 放宽规则
- `edge_case`：边界情况 → 加入评测集

#### 阶段3：归因（待实现）
自动或半自动判断问题根源：

| 违规模式 | 可能原因 | 建议动作 |
|---------|---------|---------|
| 同一术语多次违规 | prompt 未明确禁止 | 更新 prompt 黑名单 |
| 命盘数据引用错误 | 代码传参错误 | 修复 chart_data 传递 |
| 结构不符合 schema | Pydantic 校验应拦截 | 检查 schema 定义 |
| LLM 软性评分低 | 生成质量不稳定 | 优化 prompt 或换模型 |

#### 阶段4：改进（待实现）
根据归因结果执行对应改进：
- **调整 prompt**：更新 `skill_prompts.py` 或 `followup_structured.py`
- **修复代码**：修复排盘算法、数据传递等
- **更新规则**：调整评测检查器的阈值或逻辑

#### 阶段5：验证（部分实现）
- 运行 `run_batch_eval()` 验证改进效果
- 对比改进前后的 L1/L2/L3 通过率

## 四、标准评测流程设计建议

### 4.1 日常监控流程

```
每日自动执行：
1. 收集前一天所有生产监控数据
2. 统计各层级通过率
3. 识别新增违规模式
4. 生成日报（发送到飞书/邮件）
```

### 4.2 版本发布前流程

```
发布前必做：
1. 运行完整评测集 (run_batch_eval)
2. 对比基线版本的 L1/L2/L3 通过率
3. 确保无回归（通过率不低于基线）
4. 如有新增 badcase，加入评测集
```

### 4.3 问题驱动改进流程

```
发现问题时：
1. 在生产监控页面定位问题报告
2. 分析违规类型和根因
3. 选择改进方向：
   - Prompt 问题 → 修改 prompt → 重新评测
   - 代码 Bug → 修复代码 → 添加回归测试
   - 规则过严 → 调整阈值 → 记录变更原因
4. 将问题报告加入评测集防止回归
5. 验证改进效果
```
