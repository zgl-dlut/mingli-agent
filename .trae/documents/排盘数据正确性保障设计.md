# 排盘数据正确性保障设计

## Summary

当排盘出现异常时，当前架构会让整个 `generate_full_analysis` 崩溃，外层把 `analysis_data` 置为 `{}`，最终给用户一份 8 字段全空的降级报告。本方案分两层解决：**先防崩溃让字段完整（局部失败不影响全局），再诊断并修复算法 bug 让数据算得对**，降级策略保留但优化日志便于排查。

---

### 第9步组装的隐患（orchestrator.py:440-466）
result 字典用硬下标取值，如 `wangshuai_result["conclusion"]`、`geju_result["geju_type"]`、`tiaohou_result["yongshen"]`。任一 skill 返回结构异常（缺 key）→ KeyError → 整个函数崩溃。

### 已知算法 bug（project_memory 记录，需诊断确认）
project_memory 列出三类历史问题，但 Phase 1 探索发现代码现状与之**部分矛盾**，不能盲信：
- **十神阴干正偏全反**：`calculate_shishen`（bazi_service.py:793）经推演五行+阴阳逻辑**正确**，bug 可能在 `_build_shishen_map`（orchestrator.py:55）或 `geju_skill` 内部，需诊断定位
- **流月数据缺失**：`get_key_years`（dayun_liunian_skill.py:943）**已调用 `analyze_liuyue`** 并写入 `liuyue` 字段，并非完全缺失，需诊断是何路径下丢数据
- **节气交接≤1天误差**：`calculate_year_pillar`/`calculate_month_pillar`（bazi_service.py:742/752）用预计算节气表（精确到秒，来源 udtool.com），交接日命例需实测验证

## Proposed Changes（分阶段实施）

### 阶段 1：防崩溃兜底（保证字段完整，不全盘皆空）

**目标**：单个 skill 异常只影响对应字段，不让整个排盘崩溃。基础排盘（calculate_bazi）是根，失败时向上抛明确异常让上层降级。

#### 1.1 基础排盘加异常上下文
- **文件**：`app/skills/orchestrator.py` line 249
- **改法**：`calculate_bazi` 调用包一层 try/except，捕获后 `raise RuntimeError(f"基础排盘失败: {birth_date} {birth_time}, 原始异常: ...") from e`
- **为什么**：基础排盘算不出四柱，后续所有 skill 都无法运行，必须让上层走降级路径，不能假装有数据。但要把原始异常包装清楚便于排查。

#### 1.2 中间 skill 局部容错
- **文件**：`app/skills/orchestrator.py` line 269-438（第2/3/4/5/7/8.5 步）
- **改法**：每步独立 try/except，失败时该字段填 `""`（空字符串，由下游 `_build_context_vars` 的 `or MISSING_MARKER` 兜底转成"（命盘数据缺失）"），记 `logger.warning(f"[步骤X] {skill名} 计算失败，该字段置空: {e}", exc_info=True)`
- **为什么**：地支关系、旺衰、调候、格局、五行应用、命格箴言互相独立，一个失败不该连累其他。占星已有此模式，照搬。
- **注意**：第3步旺衰失败会让 `wangshuai_result` 未定义，第5步格局依赖 `wangshuai_result["conclusion"]`。容错后要给 `wangshuai_result` 设默认值 `{"conclusion":"","de_ling":{},"de_di":{},"de_shi":{},"total_score":0}`，否则下游 KeyError。

#### 1.3 第9步组装改安全取值
- **文件**：`app/skills/orchestrator.py` line 440-466
- **改法**：所有 `skill_result["key"]` 改 `skill_result.get("key", "")`，`geju_result.get("xi_ji", {})` 已是 get 但 `geju_result["geju_type"]` 是硬下标，统一改 get
- **为什么**：防 skill 返回结构异常时 KeyError 崩溃

#### 1.4 降级时日志增强
- **文件**：`app/services/ai_service.py` line 282-286、`app/services/followup_structured.py` line 671-675
- **改法**：`chart_ok=False` 时，warning 里追加 `get_chart_fingerprint(analysis_data)`（命盘指纹，含日主/四柱摘要）和缺失字段清单。关键字段（日主/四柱/用神/当前大运）缺失时日志级别升 `logger.error`
- **为什么**：降级保留，但要能在日志里快速定位是哪个 skill 挂了、命盘是什么

### 阶段 2：算法 bug 诊断与修复（让数据算得对）

**目标**：先写诊断测试确认 project_memory 里的"已知 bug"是否仍存在、在哪，再针对性修。不盲改。

#### 2.1 新建诊断测试套件
- **文件**：`backend/tests/test_paipan_correctness.py`（新建）
- **内容**：用 3-5 个已知命例（含阴干日主如乙木、节气交接日如立春当天、跨年命例）断言：
  - 四柱与公认结果一致
  - 十神正偏：阴干日主（乙/丁/己/辛/癸）的财/官/印正偏不反
  - 流月：每个重点流年的 `liuyue` 字段有 12 个月数据
  - 节气交接日：立春前后年柱正确、各节气当天月柱正确
- **为什么**：project_memory 与代码现状矛盾，必须先实测定位真实 bug，避免改了不该改的

#### 2.2 针对 bug 定位后修复
- 根据诊断测试结果，定位真实 bug 位置（可能是 `_build_shishen_map`、`geju_skill`、或节气表边界判断）
- 修复后诊断测试转绿
- **不预设具体改哪行**，等诊断结果出来再定

## Assumptions & Decisions（假设与决策）

1. **降级策略保留**：排盘失败仍降级生成报告（用户明确选择），缺失字段填 MISSING_MARKER，不拒绝生成
2. **基础排盘失败仍抛异常**：calculate_bazi 是根，算不出就让它向上抛，由 ai_service 的 except 兜底成空 dict 走降级。不假装有部分四柱数据
3. **算法 bug 先诊断后修**：project_memory 记录与代码现状矛盾（calculate_shishen 逻辑正确、流月有调用），不能盲信历史记录，必须先写测试确认
4. **不动 prompt 链路**：本方案只改排盘数据生成层，prompt 和 LLM 调用不变
5. **不动前端**：降级行为不变，前端无感知，无需改动
