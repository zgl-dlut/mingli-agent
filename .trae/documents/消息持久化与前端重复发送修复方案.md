# 消息持久化与前端重复发送修复方案

## Summary

当前用户问题和 AI 回复**没有真正落库**：前端用的是 chat_lite.py（无 DB 依赖，纯内存 job_store），而已实现存库的 chat.py 未被使用。前端靠 localStorage + addMessage 本地管理消息，多层去重仍可能导致"发送2次"。

本方案将前端切换到 chat.py（已有存库 + getMessages），消息展示以**后端为准**——发送后从后端拉取消息列表，前端不再本地 addMessage，从根本上消除重复。

## Current State Analysis

### 后端（两套路由并存）
- **chat.py**（`/api/chat/sessions/{id}/messages`）：有 DB 存储逻辑，存用户消息 + AI 回复到 chat_messages 表，有扣积分，有 getMessages 接口。**但前端没用它**。
- **chat_lite.py**（`/api/chat/analyze-jobs/{job_id}`）：无 DB 依赖，job 存内存字典（job_store.py#L32 `_jobs`），服务重启即丢失。**前端实际用的是这个**。
- 两者的 AI 生成底层相同：`generate_follow_up`（chat.py）= `generate_ai_response`（chat_lite）的包装（ai_service.py#L165-172）。

### 前端
- **chatStore.ts**：消息存 localStorage（`mingli_chats`），`fetchMessages` 从 localStorage 读，不调后端。
- **Chat.tsx handleSend**（#L577-766）：第702行本地 addMessage 用户消息，第753行本地 addMessage AI 回复，第689行前端扣积分，用 analyzeJobStream（chat_lite）。
- **recovery 逻辑**（#L360-448）：页面重载恢复 pendingJobs，第427行 addMessage AI 回复，虽有去重但依赖内容完全匹配。
- **无 session 概念**：前端用 personId，不知道 session_id。

### "发送2次"根因
前端本地 addMessage 管理 + recovery 双写。去重逻辑依赖内容完全匹配，normalize 后细微差异即失效。

## Proposed Changes

### 1. 后端：chat.py stream_response 增加存库完成标记

**文件**：`backend/app/api/chat.py`（send_message 的 stream_response，#L158-173）

**问题**：stream_response 在 yield 完所有 chunk 后才 db.commit 存 AI 回复。前端 SSE 结束时存库可能未完成，立即调 getMessages 拉不到 AI 回复。

**改法**：在 db.commit 后，yield 一个特殊标记 `\n\n__SAVED__`，前端识别后拉取。

```python
async def stream_response() -> AsyncGenerator[str, None]:
    full_content = ""
    async for chunk in generate_follow_up(system_prompt, history_list, request.content):
        full_content += chunk
        yield chunk
    
    normalized_content = normalize_output(full_content)
    assistant_message = ChatMessage(
        session_id=session_id,
        role="assistant",
        content=normalized_content,
    )
    db.add(assistant_message)
    await db.commit()
    yield "\n\n__SAVED__"  # 存库完成标记
```

同样改 get_first_reading 的 stream_response（#L208-231）。

return {

### 3. 前端：获取并存储 session_id

**文件**：`frontend/src/pages/Chat.tsx`（初始化 useEffect，person 变化时）

**改法**：person 变化时，调 `chatApi.getSessions()` 匹配 person_id 获取 session_id，存到 state。

```tsx
const [sessionId, setSessionId] = useState<number | null>(null)

useEffect(() => {
  if (!person) return
  chatApi.getSessions().then(sessions => {
    const s = sessions.find(s => s.person_id === person.id)
    if (s) setSessionId(s.id)
  })
}, [person?.id])
```

### 6. 前端：chatStore.fetchMessages 改为异步调后端

**文件**：`frontend/src/store/chatStore.ts`（#L78-84）

**改法**：fetchMessages 改为异步，调 chatApi.getMessages 拉取。

```ts
fetchMessages: async (personId, sessionId) => {
  const messages = await chatApi.getMessages(sessionId)
  const mapped = messages.map(m => ({ id: m.id, role: m.role, content: m.content, created_at: m.created_at }))
  if (!allChats[personId]) allChats[personId] = { personId, messages: [], firstReadingGenerated: false }
  allChats[personId].messages = mapped
  saveAllChats(allChats)
  set({ messages: mapped, currentPersonId: personId, currentMessage: '', isGenerating: false, streamingPersonId: null })
}
```

localStorage 保留作为缓存（离线兜底），但消息来源以后端为准。

## Assumptions & Decisions

1. **generate_follow_up 可用**：已确认它是 generate_ai_response 的包装，AI 生成质量不变。
2. **session_id 获取**：通过 getSessions 匹配 person_id。创建新 person 时 person.py 返回 session_id（改动2）。
3. **__SAVED__ 标记**：确保后端存库完成后再拉取，避免时序问题。前端过滤该标记不显示。
4. **积分扣减**：追问由后端 chat.py 扣（已有逻辑），前端删除扣减 + 刷新显示；首次解读保留前端扣（chat.py 的 first-reading 不扣）。
5. **localStorage 保留**：作为离线缓存，但消息来源以后端为准，避免本地 addMessage 导致重复。
6. **断线重连**：放弃 job_id 机制。页面重载时从后端 getMessages 拉取历史兜底。如果 AI 生成中断，用户重新发送即可（后端不会重复扣积分，因为 send_message 每次都是新请求）。

## Verification

1. **发送追问**：输入问题发送，确认用户消息只显示1次，AI 回复只显示1次。
2. **刷新页面**：刷新后消息从后端加载，历史完整保留。
3. **积分扣减**：追问后积分减少40，前端显示同步。
4. **首次解读**：生成首次解读，确认只显示1次，刷新后保留。
5. **数据库验证**：`SELECT * FROM chat_messages ORDER BY id DESC LIMIT 10;` 确认消息已落库，无重复。
6. **无 __SAVED__ 泄露**：确认界面上不显示 `__SAVED__` 标记。
