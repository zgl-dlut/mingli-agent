# AI 产品评测：人工审核方法论

## 一、人工审核应该审核什么？

### 1.1 自动化检测 vs 人工审核的分工

| 维度 | 自动化检测 | 人工审核 |
|------|-----------|---------|
| **客观违规** | ✅ 术语黑名单、JSON 格式、字数限制 | ❌ 不需要 |
| **编造检测** | ✅ 命盘实体比对 | ⚠️ 边界案例复核 |
| **叙事质量** | ️ 部分（字数、结构） | ✅ 通顺性、故事感、情感共鸣 |
| **问题匹配度** | ⚠️ 关键词重叠 | ✅ 是否真正回答用户问题 |
| **术语风格** | ❌ 无法判断 | ✅ 融合式 vs 括号标签式 |
| **新违规类型** | ❌ 未定义 | ✅ 发现并定义新规则 |

### 1.2 人工审核的三大场景

#### 场景 1：生产报告抽样审核（日常）

**审核对象**：随机抽样的生产报告（如每天 10-20 条）

**审核清单**：
```
□ 1. 问题匹配度：报告是否真正回答了用户问题？
   - 用户问"有没有钱+来源"，报告是否围绕这两个点？
   - 是否有跑题（如扩展到求职策略、领导画像）？

□ 2. 叙事质量：读起来是否通顺、有故事感？
   - 术语使用是否自然（融合式）？
   - 是否有括号标签式（不合格）？
   - 是否有"被理解"的情感共鸣？

□ 3. 命盘依据：术语是否有命盘数据支撑？
   - 提到的十神/用神/大运是否在命盘中？
   - 是否有编造（如命盘没有的干支）？

□ 4. 专业性 vs 可读性平衡：
   - 小白能否读懂？（每个术语后有大白话解释）
   - 老用户是否觉得专业？（有命理推演逻辑）

□ 5. 安全性：是否有不当承诺或误导？
   - 是否承诺具体结果（如"一定能拿到 50 万"）？
   - 是否有心理/法律/医疗方面的不当建议？
```

**审核结果**：
- 通过（质量合格）
- 需改进（有小问题但不严重）
- 不合格（有严重问题，需加入 badcase 集）

#### 场景 2：自动化检测结果复核（定期）

**审核对象**：自动化检测的误报/漏报案例

**审核清单**：
```
□ 1. 误报确认：自动化标记的违规是否真的是违规？
   - 例：标题"拿到这笔钱的关键前置动作"被标记为"未贴合用户原话"
   - 人工判断：是否合理？是否需要调整检查器？

□ 2. 漏报确认：自动化未检测到的违规
   - 例：报告编造了命盘没有的信息，但检查器未检测到
   - 人工判断：是否需要新增检查规则？

□ 3. 合格线验证：当前合格线是否合理？
   - 通过率 60% 是否太高/太低？
   - 叙事性评分 70 分是否合理？
```

**输出**：
- 调整检查器规则（如修改 regex、调整阈值）
- 新增检查项（如发现新的违规类型）
- 调整合格线（基于数据反馈）

#### 场景 3：评测集维护（版本发布前）

**审核对象**：评测集中的用例

**审核清单**：
```
□ 1. 用例覆盖度：是否覆盖了主要场景？
   - 正常报告（应通过）
   - 各类违规报告（应失败）
   - 边界案例（如术语刚好在黑名单边缘）

□ 2. 用例有效性：预期结果是否正确？
   - 正面用例是否真的质量合格？
   - 负面用例是否真的存在违规？

□ 3. 用例时效性：是否需要更新？
   - prompt 修改后，旧用例是否仍然有效？
   - 是否需要新增用例覆盖新场景？
```

**输出**：
- 更新评测集（新增/修改/删除用例）
- 重新运行评测，确认检测准确率 100%

## 二、评测指标字典的合格线如何定义？

### 2.1 合格线的定义原则

**合格线不应该由人工逐条审核**，而应该：

1. **基于数据定义**：通过历史数据分析确定合理阈值
2. **分层定义**：硬性合格线（必须达到）vs 软性合格线（目标值）
3. **定期回顾**：每月/每季度回顾一次，根据产品阶段调整

### 2.2 合格线分层定义

#### 硬性合格线（必须达到，0 容忍）

| 指标 | 合格线 | 定义依据 | 审核频率 |
|------|--------|---------|---------|
| **编造检测** | 0 次 | 命盘依据是可信度的底线 | 每次发布前 |
| **术语黑名单** | 0 次 | 专业合规性要求 | 每次发布前 |
| **JSON 格式** | 100% | 技术底线，格式错误=系统 bug | 实时监控 |
| **安全性** | 0 次 | 法律/伦理底线 | 每次发布前 |

**特点**：这些指标一旦违规，报告必须被标记为"不合格"，不允许上线。

#### 软性合格线（目标值，允许波动）

| 指标 | 合格线 | 定义依据 | 审核频率 |
|------|--------|---------|---------|
| **通过率** | ≥ 60% | 历史数据 P50 水平 | 每月回顾 |
| **叙事性评分** | ≥ 70 分 | LLM 评分分布 P60 | 每月回顾 |
| **检测准确率** | ≥ 80% | 检查器有效性指标 | 每次发布前 |
| **任务完成率** | ≥ 70% | 综合质量指标 | 每月回顾 |

**特点**：这些指标允许一定波动，但长期低于合格线需要优化 prompt 或检查器。

### 2.3 合格线的定义方法

#### 方法 1：历史数据分位数法

```python
# 示例：基于历史数据定义叙事性评分合格线
scores = [65, 72, 78, 80, 85, 88, 90, 92, 95]
p60 = np.percentile(scores, 60)  # 78 分
合格线 = round(p60 / 10) * 10    # 80 分（取整）
```

**优点**：客观、数据驱动
**缺点**：需要足够的历史数据（至少 50-100 条）

#### 方法 2：人工标注校准法

```
1. 随机抽取 50 条报告
2. 人工标注"合格/不合格"
3. 计算 LLM 评分与人工标注的相关性
4. 找到最佳分界点（如 F1 最高对应的分数）
```

**优点**：与人工判断对齐
**缺点**：耗时，需要定期重新校准

#### 方法 3：业务目标倒推法

```
业务目标：用户满意度 ≥ 80%
↓
推导：报告质量评分 ≥ 75 分时，用户满意度 ≈ 80%
↓
合格线：75 分
```

**优点**：与业务目标对齐
**缺点**：需要用户满意度数据

### 2.4 合格线的审核流程

```
┌─────────────────────────────────────────┐
│           合格线审核流程                  │
├─────────────────────────────────────────┤
│ 1. 数据收集（每月）                      │
│    - 生产报告质量分布                    │
│    - 用户反馈/投诉                       │
│    - 自动化检测结果                      │
├─────────────────────────────────────────┤
│ 2. 数据分析                              │
│    - 当前合格线下的通过率                │
│    - 误报率/漏报率                       │
│    - 与用户满意度的相关性                │
├─────────────────────────────────────────┤
│ 3. 人工评审（每月一次）                  │
│    - 产品经理 + 命理专家                 │
│    - 审阅 20-30 条边界案例               │
│    - 决定是否需要调整合格线              │
├─────────────────────────────────────────┤
│ 4. 调整执行                              │
│    - 修改合格线配置                      │
│    - 更新评测集                          │
│    - 重新运行评测验证                    │
─────────────────────────────────────────┘
```

### 3.2 审核数据流

```
人工审核提交
    ↓
保存审核记录（eval_reviews 表）
    ↓
┌──────────────────┬──────────────────┬──────────────────┐
│ 审核结果=通过     │ 审核结果=需改进   │ 审核结果=不合格   │
│                  │                  │                  │
│ 标记为高质量报告  │ 标记为待优化      │ 加入 badcase 集   │
│ 可用于训练数据    │ 进入优化队列      │ 自动加入评测集    │
│                  │                  │ 触发 prompt 优化   │
└──────────────────┴──────────────────┴──────────────────┘
```

### 3.3 自动加入评测集逻辑

**触发条件**：
- 审核结果 = "不合格"
- 或人工点击"加入评测集"

**自动生成的用例**：
```json
{
  "id": "review_20260813_001",
  "description": "人工审核-跑题案例",
  "user_question": "27年10月或者11月底是有一大笔资金入账的吗？资金大概是什么来源",
  "report": { ... },  // 完整报告 JSON
  "expected_pass": false,
  "expected_violations": ["标题未贴合用户原话", "subtopic跑题"],
  "review_comment": "报告扩展到求职策略、领导画像，偏离用户核心问题",
  "reviewer": "产品经理A",
  "review_date": "2026-08-13"
}
```

**自动新增评测条件**：
- 如果发现新的违规类型（如"subtopic跑题"），自动新增检查规则
- 更新检查器代码，加入新的检测逻辑

## 四、实施建议

### 4.1 第一阶段：基础人工审核（1-2 周）

**目标**：建立人工审核流程，积累标注数据

**功能**：
- 审核界面（报告详情 + 审核表单）
- 审核记录保存
- 审核结果筛选/导出

**审核量**：每天 10-20 条，持续 2 周

**输出**：
- 200-400 条人工标注数据
- 误报/漏报案例清单
- 合格线调整建议

### 4.2 第二阶段：自动化增强（2-4 周）

**目标**：基于人工标注数据优化自动化检测

**功能**：
- 自动加入评测集
- 新检查规则发现
- 合格线自动调整建议

**输出**：
- 检测准确率提升至 90%+
- 误报率降低至 10% 以下

### 4.3 第三阶段：闭环优化（持续）

**目标**：建立持续优化闭环

**流程**：
```
生产报告 → 自动化检测 → 人工抽样审核 → 发现问题
    ↓                                        ↓
优化 prompt/检查器 ← 更新评测集 ← 加入 badcase
```

**指标**：
- 检测准确率 ≥ 95%
- 通过率 ≥ 70%
- 用户满意度 ≥ 80%

## 五、常见问题 FAQ

### Q1：人工审核需要命理专业知识吗？

**A**：需要基础了解，但不需要专家级。

**审核重点**：
- 叙事质量（通顺性、故事感）→ 不需要命理知识
- 问题匹配度（是否跑题）→ 不需要命理知识
- 命盘依据（术语是否有依据）→ 需要基础了解（能看懂命盘数据即可）

**建议**：产品经理 + 命理专家各审核 50%，或产品经理审核叙事，命理专家审核依据。

### Q2：人工审核会不会太主观？

**A**：会有主观性，但可以通过以下方式降低：

1. **明确审核标准**：提供详细的审核清单和示例
2. **多人审核**：每条报告至少 2 人审核，取多数意见
3. **定期校准**：每月审核一次"标准答案"，对齐审核尺度
4. **数据驱动**：用历史数据验证审核结果的合理性

### Q3：合格线多久调整一次？

**A**：建议频率：

- **硬性合格线**：每次发布前审核（如编造检测 0 容忍）
- **软性合格线**：每月回顾一次（如通过率 60%）
- **重大调整**：每季度一次（如新增检查维度）

### Q4：人工审核的成本如何控制？

**A**：分层审核策略：

- **高风险报告**（敏感话题、负面情绪）：100% 人工审核
- **中风险报告**（自动化检测边缘）：50% 人工审核
- **低风险报告**（自动化检测通过）：5-10% 抽样审核

**成本估算**：
- 每天 100 条报告 → 约 10-20 条人工审核 → 1-2 小时/天
