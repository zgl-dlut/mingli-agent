# 评测集扩展实施计划：叙事性 + 结构 + 排盘 + 命盘数据使用

## Summary

在已有的 11 个规则正确性检测函数（集成在 `followup_structured.py` 主流程）基础上，新增四类评测能力：

* **A. 结构检查器**：子问题拆解覆盖度、blocks 数量、keyword 非空/叙事化/加粗、narrative 字数、summary 关键词叙事化

* **B. 叙事性检查器**：keyword 含术语黑名单、narrative 术语无解释、标题答非所问、元标签检测

* **C. 排盘正确性检查器**：标准命盘集回归测试（四柱/十神/大运方向）

* **D. 命盘数据使用检查器**：LLM 输出实体提取 + 与命盘数据比对（编造大运/流年/用神检测）

同时补全 **badcase 自动收集机制**（`save_badcase` 函数之前讨论但未实现），实现重试终止时自动入库，供后续提取示例动态注入 prompt。

### A. 结构检查器

**文件**：`backend/app/services/eval/structure_checker.py`（新建）

**职责**：检查报告 JSON 结构是否符合 schema 约束和 project\_memory 规则

**检查项**：

```python
def check_structure(report: dict, user_question: str) -> list[dict]:
    """返回违规列表，每项 {"type": str, "detail": str, "location": str}"""
    violations = []

    # 1. 子问题拆解覆盖度
    #    规则：用户问了几个独立的事，就有几个 subtopic 一一回应
    #    实现：用标点切分（，。？；）+ 连词识别（和/与/还有/另外）估算独立关切点
    #    容差：actual_count >= expected_count * 0.8 即通过（允许合并延伸追问）
    expected = estimate_question_count(user_question)
    actual = len(report.get("subtopics", []))
    if actual < max(1, int(expected * 0.8)):
        violations.append({"type": "子问题漏答", "detail": f"用户约{expected}个独立点，只拆了{actual}个"})

    # 2. 每个 subtopic 的 blocks 数量（2-4）
    for i, sub in enumerate(report.get("subtopics", [])):
        blocks = [b for b in sub.get("blocks", []) if isinstance(b, dict)]
        if len(blocks) < 2 or len(blocks) > 4:
            violations.append({"type": "block数量异常", "subtopic": i, "detail": f"blocks={len(blocks)}，应为2-4"})

    # 3. 每个 block 的 keyword 非空、narrative 字数 30-120
    for i, sub in enumerate(report.get("subtopics", [])):
        for j, blk in enumerate(sub.get("blocks", [])):
            kw = blk.get("keyword", "")
            nar = blk.get("narrative", "")
            if not kw.strip():
                violations.append({"type": "keyword为空", "subtopic": i, "block": j})
            if len(nar) < 30:
                violations.append({"type": "narrative过短", "subtopic": i, "block": j, "len": len(nar)})
            if len(nar) > 120:
                violations.append({"type": "narrative过长", "subtopic": i, "block": j, "len": len(nar)})

    # 4. keyword 加粗检查
    #    规则：keyword 字段本身不加 **（加粗在 narrative 内联），keyword 是纯文本短语
    for i, sub in enumerate(report.get("subtopics", [])):
        for j, blk in enumerate(sub.get("blocks", [])):
            kw = blk.get("keyword", "")
            if "**" in kw:
                violations.append({"type": "keyword含加粗标记", "subtopic": i, "block": j, "keyword": kw})

    # 5. summary items 的 keyword 叙事化
    #    规则：禁止"蹲守期/守业期/蛰伏期"等泛泛标签，需"时间+具体事件"格式
    GENERIC_PATTERNS = [r"^[蛰伏蹲守守业过渡调整观望]+期$", r"^[总结收尾点睛]+$"]
    for item in report.get("summary", {}).get("items", []):
        kw = item.get("keyword", "")
        for pat in GENERIC_PATTERNS:
            if re.match(pat, kw):
                violations.append({"type": "summary关键词泛泛", "keyword": kw})

    # 6. subtopic 标题贴合用户原话
    #    规则：标题要尽量使用用户原话关键词，可适当改写但严禁替换成命理术语
    question_keywords = extract_question_keywords(user_question)
    for i, sub in enumerate(report.get("subtopics", [])):
        title = sub.get("title", "")
        overlap = len([k for k in question_keywords if k in title])
        if overlap == 0 and question_keywords:
            violations.append({"type": "标题未贴合用户原话", "subtopic": i, "title": title})

    return violations


def estimate_question_count(question: str) -> int:
    """估算用户问题中的独立关切点数量"""
    # 按标点切分
    segments = re.split(r'[，。？；！]', question)
    segments = [s.strip() for s in segments if s.strip()]
    # 识别连词连接的并列子句
    CONNECTORS = ["和", "与", "还有", "另外", "以及", "同时", "是否", "能不能", "能不能够"]
    count = 0
    for seg in segments:
        for conn in CONNECTORS:
            if conn in seg:
                count += 1
        count += 1
    # 上限4（project_memory 规定建议拆 2-4 个）
    return min(max(1, count), 4)


def extract_question_keywords(question: str) -> list[str]:
    """提取用户问题中的关键词（用于标题贴合度检查）"""
    # 简单实现：取2-4字的名词性片段
    # 可后续接 jieba 分词优化
    return [w for w in re.findall(r'[\u4e00-\u9fa5]{2,6}', question) if len(w) >= 2][:10]
```

**集成方式**：

* 评测时：`run_eval.py` 单独调用

* 生产可选集成：在 `_normalize_report_data` 后调用，违规只告警不拦截（避免误杀）

### B. 叙事性检查器

**文件**：`backend/app/services/eval/narrative_checker.py`（新建）

**职责**：检查报告叙事性合规性（术语管控、叙事化、答非所问）

**检查项**：

```python
# 术语黑名单（与 followup_structured.py 的 _detect_forbidden_terms 保持一致）
TERM_BLACKLIST = [
    "七杀", "正官", "偏印", "正印", "伤官", "食神",
    "比肩", "劫财", "偏财", "正财", "月令", "宫位", "用神", "忌神", "日支", "流月"
]

# 元标签黑名单（project_memory：首次报告第5个block禁止用元标签）
META_LABELS = ["收尾点睛", "总结", "收尾", "小结", "结语", "归纳"]


def check_narrative(report: dict, is_first_reading: bool = False) -> list[dict]:
    violations = []

    # 1. keyword 含术语黑名单词
    for i, sub in enumerate(report.get("subtopics", [])):
        for j, blk in enumerate(sub.get("blocks", [])):
            kw = blk.get("keyword", "")
            for term in TERM_BLACKLIST:
                if term in kw:
                    violations.append({"type": "keyword含术语", "subtopic": i, "block": j, "keyword": kw, "term": term})

    # 2. narrative 中术语是否有解释（括号/= /也就是/即 紧跟）
    for i, sub in enumerate(report.get("subtopics", [])):
        for j, blk in enumerate(sub.get("blocks", [])):
            nar = blk.get("narrative", "")
            for term in TERM_BLACKLIST:
                idx = nar.find(term)
                if idx >= 0:
                    after = nar[idx+len(term):idx+len(term)+10]
                    if not any(m in after for m in ["（", "(", "=", "也就是", "即"]):
                        violations.append({"type": "术语无解释", "subtopic": i, "block": j, "term": term})

    # 3. keyword 元标签检测（首次报告第5个block专用）
    if is_first_reading:
        subtopics = report.get("subtopics", [])
        if subtopics:
            blocks = subtopics[0].get("blocks", [])  # 首次报告"命盘解码"模块
            if len(blocks) >= 5:
                kw = blocks[4].get("keyword", "")
                for meta in META_LABELS:
                    if meta in kw:
                        violations.append({"type": "keyword元标签", "block": 4, "keyword": kw, "meta": meta})

    # 4. 标题答非所问（keyword/标题必须正面回答用户问题）
    #    规则：project_memory "关键词/标题必须正面回答用户问题"
    #    实现：检查 keyword 是否包含否定式回避（如"不便回答""无法确定"）
    EVASIVE_PATTERNS = [r"不便回答", r"无法确定", r"难以判断", r"不好说"]
    for i, sub in enumerate(report.get("subtopics", [])):
        for j, blk in enumerate(sub.get("blocks", [])):
            kw = blk.get("keyword", "")
            for pat in EVASIVE_PATTERNS:
                if re.search(pat, kw):
                    violations.append({"type": "keyword回避问题", "subtopic": i, "block": j, "keyword": kw})

    return violations
```

**集成方式**：

* 评测时：`run_eval.py` 单独调用

* 生产可选集成：在现有 `_detect_forbidden_terms` 基础上扩展（keyword 字段检查）

```python
def check_chart_correctness(generated: dict, expected: dict) -> list[dict]:
    """比对排盘结果与标准答案"""
    violations = []

    # 1. 四柱干支（去空格比对）
    gen_pillars = generated.get("四柱", "").replace(" ", "")
    exp_pillars = expected.get("四柱", "").replace(" ", "")
    if gen_pillars != exp_pillars:
        violations.append({"type": "四柱错误", "expected": exp_pillars, "actual": gen_pillars})

    # 2. 日主
    gen_rizhu = generated.get("日主", "")
    exp_rizhu = expected.get("日主", "")
    if gen_rizhu != exp_rizhu:
        violations.append({"type": "日主错误", "expected": exp_rizhu, "actual": gen_rizhu})

    # 3. 十神（已知存在阴干日主正偏全反的 bug）
    gen_shishen = generated.get("十神", {})
    exp_shishen = expected.get("十神", {})
    if isinstance(gen_shishen, dict) and isinstance(exp_shishen, dict):
        for pos, exp_val in exp_shishen.items():
            gen_val = gen_shishen.get(pos, "")
            if gen_val != exp_val:
                violations.append({"type": "十神错误", "position": pos, "expected": exp_val, "actual": gen_val})

    # 4. 大运方向
    gen_dir = generated.get("大运方向", "")
    exp_dir = expected.get("大运方向", "")
    if gen_dir != exp_dir:
        violations.append({"type": "大运方向错误", "expected": exp_dir, "actual": gen_dir})

    # 5. 起运年龄
    gen_start = generated.get("起运", "")
    exp_start = expected.get("起运", "")
    if exp_start and gen_start != exp_start:
        violations.append({"type": "起运错误", "expected": exp_start, "actual": gen_start})

    return violations
```

```python
def extract_chart_entities(report: dict) -> dict:
    """从 LLM 输出中提取所有命理相关实体"""
    entities = {"大运": set(), "流年": set(), "十神": set(), "用神": set(), "忌神": set()}
    all_text = json.dumps(report, ensure_ascii=False)

    # 大运干支：匹配"甲寅大运""甲寅运"
    for m in re.finditer(r"([甲乙丙丁戊己庚辛壬癸][子丑寅卯辰巳午未申酉戌亥])[运大]*运", all_text):
        entities["大运"].add(m.group(1))

    # 流年干支：匹配"2034年甲寅"
    for m in re.finditer(r"(\d{4})年([甲乙丙丁戊己庚辛壬癸][子丑寅卯辰巳午未申酉戌亥])", all_text):
        entities["流年"].add(f"{m.group(1)}:{m.group(2)}")

    # 十神（黑名单术语）
    shishen_terms = ["七杀", "正官", "偏印", "正印", "伤官", "食神", "比肩", "劫财", "偏财", "正财"]
    for term in shishen_terms:
        if term in all_text:
            entities["十神"].add(term)

    # 用神/忌神：匹配"用神X""忌神X"
    for m in re.finditer(r"用神[是为]?([\u4e00-\u9fa5])", all_text):
        entities["用神"].add(m.group(1))
    for m in re.finditer(r"忌神[是为]?([\u4e00-\u9fa5])", all_text):
        entities["忌神"].add(m.group(1))

    return entities


def extract_chart_data_entities(chart_data: dict) -> dict:
    """从命盘数据中提取所有合法实体"""
    entities = {"大运": set(), "流年": set(), "十神": set(), "用神": set(), "忌神": set()}

    # 大运：从"当前大运"和"大运列表"提取
    current_dayun = chart_data.get("当前大运", "")
    for m in re.finditer(r"([甲乙丙丁戊己庚辛壬癸][子丑寅卯辰巳午未申酉戌亥])", current_dayun):
        entities["大运"].add(m.group(1))

    # 流年：从"重点流年"提取
    key_liunian = chart_data.get("重点流年", [])
    if isinstance(key_liunian, list):
        for item in key_liunian:
            text = str(item)
            # 匹配"2034年""甲寅"
            year_m = re.search(r"(\d{4})年", text)
            gz_m = re.search(r"([甲乙丙丁戊己庚辛壬癸][子丑寅卯辰巳午未申酉戌亥])", text)
            if year_m and gz_m:
                entities["流年"].add(f"{year_m.group(1)}:{gz_m.group(1)}")

    # 用神/忌神
    yongshen = chart_data.get("用神", "")
    if yongshen:
        for m in re.finditer(r"([\u4e00-\u9fa5])", yongshen):
            entities["用神"].add(m.group(1))
    jishen = chart_data.get("忌神", "")
    if jishen:
        for m in re.finditer(r"([\u4e00-\u9fa5])", jishen):
            entities["忌神"].add(m.group(1))

    return entities


def check_chart_usage(report: dict, chart_data: dict) -> list[dict]:
    """检查 LLM 输出是否编造了命盘未提供的数据"""
    violations = []
    report_entities = extract_chart_entities(report)
    chart_entities = extract_chart_data_entities(chart_data)

    # 1. 大运：LLM 提到的大运干支必须在命盘大运列表中
    for dy in report_entities["大运"]:
        if dy not in chart_entities["大运"]:
            violations.append({"type": "编造大运", "entity": dy, "命盘已有": list(chart_entities["大运"])})

    # 2. 流年：LLM 提到的流年干支必须在重点流年列表中
    #    容差：年份在命盘流年列表中但干支不同 → 告警（可能排盘算法bug）
    chart_years = {ln.split(":")[0] for ln in chart_entities["流年"]}
    for ln in report_entities["流年"]:
        year, gz = ln.split(":")
        if ln not in chart_entities["流年"]:
            if year in chart_years:
                violations.append({"type": "流年干支不一致", "entity": ln, "命盘已有": list(chart_entities["流年"])})
            else:
                violations.append({"type": "编造流年", "entity": ln, "命盘已有": list(chart_entities["流年"])})

    # 3. 用神/忌神：与命盘一致
    for ys in report_entities["用神"]:
        if ys not in chart_entities["用神"]:
            violations.append({"type": "用神不一致", "expected": chart_data.get("用神", ""), "actual": ys})

    for js in report_entities["忌神"]:
        if js not in chart_entities["忌神"]:
            violations.append({"type": "忌神不一致", "expected": chart_data.get("忌神", ""), "actual": js})

    return violations
```

### E. LLM 评分器（分层评分：硬性错误一票否决 + 软性质量补充）

**文件**：`backend/app/services/eval/llm_scorer.py`（新建）

**核心设计原则**：**分层评分，硬性错误一票否决**

* **第一层 硬性检查**（代码层检查器，快、确定性强）：结构错误、术语违规、命盘数据编造、排盘错误 → 任何一项违规，直接判定 overall\_pass=false，不再跑 LLM 软性评分

* **第二层 软性评分**（LLM 评分器，仅在硬性检查全通过时执行）：叙事性、通顺性、故事性、加粗合理性 → 评估"好不好的问题"，不是"对不对的问题"

**为什么硬性错误一票否决**：

* 报告有结构错误（子问题漏答/keyword 为空）→ 用户看不懂，叙事性再好没用

* 报告有命盘数据编造（编造大运/流年）→ 内容错误，叙事性是误导

* 报告有术语违规（keyword 含"七杀/正官"）→ 违反 project\_memory 硬约束，叙事性无意义

* **结论**：硬性错误是"对错问题"，叙事性是"好坏问题"，对错优先于好坏

```python
async def evaluate_report(
    report: dict,
    user_question: str,
    chart_data: dict,
    is_first_reading: bool = False,
) -> dict:
    """分层评分主入口：硬性检查 → 软性评分

    返回结构：
    {
        "overall_pass": bool,           # 综合是否合格
        "hard_check": {                 # 第一层：硬性检查（代码层）
            "passed": bool,
            "violations": [...],        # 结构/叙事性/命盘数据/术语 违规列表
            "blocked_by": "structure"   # 被哪类硬性检查拦截（None=全通过）
        },
        "soft_score": {                 # 第二层：软性评分（仅硬性通过时才有值）
            "叙事性": 4, "通顺性": 5, ...,
            "问题": ["..."]
        } | None,
        "fabrication": {...} | None     # 编造检测（仅硬性通过时才跑）
    }
    """
    # ===== 第一层：硬性检查（代码层，不调用LLM，快）=====
    from app.services.eval.structure_checker import check_structure
    from app.services.eval.narrative_checker import check_narrative
    from app.services.eval.chart_usage_checker import check_chart_usage

    structure_violations = check_structure(report, user_question)
    narrative_violations = check_narrative(report, is_first_reading)
    chart_usage_violations = check_chart_usage(report, chart_data)

    all_hard_violations = structure_violations + narrative_violations + chart_usage_violations
    hard_passed = len(all_hard_violations) == 0

    # 确定被哪类硬性检查拦截（用于报告诊断）
    blocked_by = None
    if not hard_passed:
        if structure_violations:
            blocked_by = "structure"
        elif narrative_violations:
            blocked_by = "narrative"
        elif chart_usage_violations:
            blocked_by = "chart_usage"

    hard_check = {
        "passed": hard_passed,
        "violations": all_hard_violations,
        "blocked_by": blocked_by,
        "structure_count": len(structure_violations),
        "narrative_count": len(narrative_violations),
        "chart_usage_count": len(chart_usage_violations),
    }

    # ===== 硬性检查未通过 → 直接判定不合格，跳过软性评分 =====
    if not hard_passed:
        return {
            "overall_pass": False,
            "hard_check": hard_check,
            "soft_score": None,       # 不跑软性评分（硬性错误时叙事性无意义）
            "fabrication": None,
            "skip_reason": f"硬性检查未通过(blocked_by={blocked_by})，跳过软性评分",
        }

    # ===== 第二层：软性评分（仅硬性检查全通过时执行）=====
    soft_score = await llm_score_narrative(report, user_question)
    fabrication = await llm_check_fabrication(report, chart_data)

    # 编造检测有 high 严重程度 → 也判定不合格
    fab_blocked = (
        fabrication.get("编造") is True
        and fabrication.get("严重程度") == "high"
    )

    # 软性评分门槛：各维度平均分 >= 70（1-100分制）
    scores = [v for k, v in soft_score.items() if k not in ("问题",) and isinstance(v, (int, float))]
    avg_score = sum(scores) / len(scores) if scores else 0

    return {
        "overall_pass": (not fab_blocked) and (avg_score >= 70),
        "hard_check": hard_check,
        "soft_score": soft_score,
        "fabrication": fabrication,
        "avg_soft_score": round(avg_score, 2),
    }


async def llm_score_narrative(report: dict, user_question: str) -> dict:
    """用 qwen-flash 对报告打分（1-100分），仅在硬性检查通过后调用"""
    prompt = f"""请对以下命理追问报告评分（1-100分），评估维度：
    1. 叙事性：是否像给朋友讲故事，有起承转合
    2. 通顺性：语句是否流畅自然
    3. 故事性：是否有故事感，不堆砌术语
    4. 加粗合理性：**加粗**是否用在关键词上，不滥用
    5. 术语通俗化：命理术语是否用括号/= /也就是紧跟解释

    注意：结构/术语/命盘数据等硬性错误已由代码检查器覆盖，你只需评估软性质量。

    用户问题：{user_question}
    报告：{json.dumps(report, ensure_ascii=False)[:3000]}

    输出JSON：{{"叙事性": 85, "通顺性": 90, "故事性": 75, "加粗合理性": 88, "术语通俗化": 82, "问题": ["..."]}}
    """
    return await _call_llm(prompt)


async def llm_check_fabrication(report: dict, chart_data: dict) -> dict:
    """用 LLM 判断输出是否编造了命盘未提供的信息（语义层补充，代码层 chart_usage_checker 已做正则提取）"""
    prompt = f"""命盘数据（权威来源）：
    {json.dumps(chart_data, ensure_ascii=False)[:2000]}

    LLM 生成的报告：
    {json.dumps(report, ensure_ascii=False)[:3000]}

    请检查报告是否编造了命盘未提供的信息：
    1. 是否提到了命盘未列出的大运？
    2. 是否提到了命盘未列出的流年？
    3. 是否自行判定了用神/忌神（与命盘不一致）？
    4. 是否提到了命盘未列出的十神？

    输出JSON：{{"编造": true/false, "编造内容": ["..."], "严重程度": "high/medium/low"}}
    """
    return await _call_llm(prompt)


async def _call_llm(prompt: str) -> dict:
    """调用 qwen-flash，复用 model_pool"""
    from app.services.ai_service import model_pool, get_client, build_llm_extra_body
    if not model_pool:
        return {"error": "model_pool 为空"}
    # 优先用 flash 模型，没有就用主模型
    flash_models = [m for m in model_pool if "flash" in m.name]
    model_config = flash_models[0] if flash_models else model_pool[0]
    client = await get_client(model_config)
    response = await client.chat.completions.create(
        model=model_config.name,
        messages=[{"role": "user", "content": prompt}],
        temperature=0.1,
        max_tokens=1000,
        response_format={"type": "json_object"},
        timeout=30,
        extra_body=build_llm_extra_body(model_config.name),
    )
    raw = response.choices[0].message.content or ""
    return json.loads(raw)
```

**分层评分的价值**：

* **节省成本**：硬性错误报告不跑 LLM 软性评分（省 2 次 LLM 调用）

* **结果更可信**：硬性检查是确定性判断（正则/结构比对），不受 LLM 随机性影响

* **诊断更清晰**：`blocked_by` 字段直接告诉用户是哪类硬性错误导致的失败，而不是笼统的"叙事性 2 分"

**业界实践对照**（LLM 评测 4 大方法，我们的方案覆盖其中 3 种）：

| 业界方法                           | 我们方案中的对应                                        | 适用场景                            |
| ------------------------------ | ----------------------------------------------- | ------------------------------- |
| Verifiers（规则检查器）               | 结构检查器、叙事性检查器、命盘数据检查器、排盘检查器                      | 硬性约束（JSON 格式、字段非空、术语黑名单、命盘数据比对） |
| LLM-as-a-Judge（LLM 评委）         | `llm_score_narrative` + `llm_check_fabrication` | 主观质量（叙事性、通顺性、故事性、编造检测）          |
| Reference Comparison（标准答案对比）   | 排盘回归测试（`eval_chart_dataset.json`）               | 有明确正确答案的任务（四柱/十神/大运方向）          |
| Model-Based Classifiers（训练分类器） | 暂不采用（需标注数据，成本高）                                 | 高频错误模式规模化检测                     |

**业界共识**：组合使用多种方法，规则检查负责"对错"，LLM 评委负责"好坏"，标准答案负责"准确性"。我们的分层评分设计完全符合这一共识。

**LLM-as-a-Judge 的已知风险与缓解**（业界研究指出 LLM 评委存在偏差和鲁棒性问题）：

| 风险                 | 业界发现                                   | 我们的缓解措施                                       |
| ------------------ | -------------------------------------- | --------------------------------------------- |
| **位置偏差**           | LLM 倾向于偏好第一个或最后一个候选                    | 我们是单报告打分（非成对比较），不存在位置偏差                       |
| **长度偏差**           | LLM 倾向于给更长的回答更高分                       | 评分 prompt 明确"长度不作为评分依据"，且 narrative 有 120 字上限 |
| **风格偏差**           | LLM 偏好特定写作风格                           | 用清晰 rubric（1-5 分各维度明确标准），减少主观偏好               |
| **"Master Key"攻击** | 简单符号（如"Thought process:"）能骗过 LLM 评委给高分 | 分层评分——硬性检查一票否决，即使 LLM 被骗给高分，硬性错误仍会拦截          |
| **一致性波动**          | 同一输入多次评分结果不一致                          | 评测时同一报告跑 3 次取平均；生产环境只告警不拦截                    |
| **人工校准缺失**         | LLM 评委标准与人工不一致                         | 初期用 10-20 个人工标注样本校准 rubric，后续定期复核             |

### F. badcase 自动收集

**核心原则**：badcase 入库后，注入 prompt 的不是完整示例内容（用户问题+命盘+完整报告，token 太长），而是从 badcase 中**提炼的"违规原因+修正方向"精简规则**（50-150字），作为新的规则条目追加到 system\_prompt 规则区。

**注入方式对比**：

* ✅ 规则注入（采用）：`"禁止把'需注意'放大成'不适合启动'——吉年整体方向利启动，'需注意'只是附带提醒"`（50字）

* ❌ 完整示例注入（不采用）：`"示例：用户问X，命盘Y，错误输出Z，正确应该是W"`（500+字）

```python
async def save_badcase(
    person_id: int,
    question: str,
    chart_fingerprint: dict,
    violation_type: str,
    violation_detail: str,
    raw_output: str,
```

**规则注入流程**（badcase → prompt 的精简链路）：

```
1. 自动收集：重试终止 → save_badcase 入库（reviewed=0）
2. 人工审核：后台查看 badcase 详情 → 分析违规根因 → 填写 extracted_rule（50-150字精简规则）+ rule_category
   例：extracted_rule = "吉年'reason含需注意'不等于'不适合启动'，必须给出鼓励方向，'需注意'只是附带提醒"
3. 规则注入：build_structured_prompt 构造时，查询 reviewed=2 的 badcase，把 extracted_rule 追加到对应分类的规则区
   - 只注入 extracted_rule 文本（50-150字），不注入 question/chart_fingerprint/raw_output
   - 按规则分类（rule_category）追加到对应章节末尾
4. 状态更新：注入后 reviewed=3，避免重复注入
```

**token 成本对比**：

* 完整示例注入：每个 badcase 约 800-1500 token（问题+命盘+报告）

* 精简规则注入：每个 badcase 约 50-150 token（只注入规则）

* 10 个 badcase 注入：完整示例 8000-15000 token vs 精简规则 500-1500 token

```python
"""评测运行器：跑完整评测集，使用分层评分（硬性检查一票否决 + 软性评分补充）"""
import asyncio
import json
from app.skills.orchestrator import generate_full_analysis
from app.services.followup_structured import generate_followup_structured
from app.services.eval.llm_scorer import evaluate_report  # 分层评分主入口


async def run_eval(dataset_path: str = "tests/eval_dataset.json"):
    dataset = load_json(dataset_path)
    results = []
    for case in dataset:
        # 1. 生成命盘
        chart_data = generate_full_analysis(**case["person"])
        # 2. 生成报告
        report_raw = ""
        async for chunk in generate_followup_structured(
            analysis_data=chart_data,
            user_question=case["question"],
            # ... 其他参数
        ):
            report_raw += chunk
        report = json.loads(report_raw)
        # 3. 分层评分（硬性检查一票否决 + 软性评分补充）
        eval_result = await evaluate_report(
            report=report,
            user_question=case["question"],
            chart_data=chart_data,
            is_first_reading=case.get("is_first_reading", False),
        )
        result = {
            "id": case["id"],
            "category": case["category"],
            "overall_pass": eval_result["overall_pass"],
            "hard_check": eval_result["hard_check"],       # 硬性检查结果（结构/叙事性/命盘数据）
            "soft_score": eval_result.get("soft_score"),   # 软性评分（硬性通过时才有值）
            "fabrication": eval_result.get("fabrication"), # 编造检测（硬性通过时才有值）
            "skip_reason": eval_result.get("skip_reason"), # 跳过软性评分的原因
        }
        results.append(result)
    # 4. 汇总输出
    print_summary(results)
    save_report(results, "tests/eval_report.json")
```

## Assumptions & Decisions

1. **检查器独立模块化**：所有检查器放在 `app/services/eval/` 目录，评测时单独调用，不污染 `followup_structured.py` 主流程。生产环境可选集成（违规只告警不拦截）。

2. **LLM 评分用 qwen-flash + 分层评分机制 + 1-100分制**：评分任务简单，用轻量模型节省成本。复用现有 `model_pool`，优先选 flash 模型。**关键设计**：分层评分——硬性检查（结构/术语/命盘数据）一票否决，软性评分（叙事性/通顺性）仅在硬性通过时执行。硬性错误时叙事性无意义，避免"错误报告得高分"的悖论。**评分制**：各维度用 1-100 分（与现有反馈服务的 `model_self_score` 保持一致，1-5 分拉不开差距），软性评分门槛 70 分。

3. **排盘标准答案手工构造**：初始 10 个命盘覆盖核心场景（阴干/阳干日主、节气交接、子时跨日），标准答案用权威排盘工具生成。已知 bug 用 `known_bug: true` 标注，回归测试时 xfail。

4. **命盘实体提取用正则**：大运/流年干支有固定格式（天干+地支），正则可靠提取。复杂语义判断（如"换组"是否答成"换工位"）由现有 `_detect_dimension_coverage` 覆盖，不重复实现。

5. **badcase 注入的是精简规则而非完整示例**：重试终止时自动入库（`person_id` 从调用方传入）。人工审核后，从 badcase 中提炼"违规原因+修正方向"精简规则（50-150字），填入 `extracted_rule` 字段。注入 prompt 时只追加这条精简规则到 system\_prompt 规则区，**不注入完整案例内容**（用户问题+命盘+报告动辄上千 token，会导致 prompt 膨胀）。注入逻辑本次不实现，留作下一步。

6. **评测集 JSON 文件管理**：方便版本管理和 diff，不入库。初始 5-10 个 case，后续根据 badcase 扩展。

7. **反馈服务整合到评测中心**：现有 `feedback_service` 的"反馈看板"菜单整合到"评测中心"作为一个 tab（线上反馈），统一质量看板入口。反馈服务的 `model_self_score`（单维度 1-100 分）本次保留不动，后续可升级为多维度评分。**不改动反馈服务代码**，只做前端菜单整合（FeedbackDashboard 组件作为评测中心的子 tab 复用）。

7. **评测执行时机：三层评测架构**（业界标准实践——L1 在线拦截 + L2 在线影子监控 + L3 离线全量评测，三者职责分离，互不干扰）：

   | 层级            | 执行时机          | 跑什么                                       | 作用                                 | 性能影响                     |
   | ------------- | ------------- | ----------------------------------------- | ---------------------------------- | ------------------------ |
   | **L1 在线自检**   | 每次生成报告（已有）    | 现有 11 个自检函数（凶年启动/术语黑名单/同义词对立等）            | 拦截严重违规、触发重试、badcase 入库             | 已在生产中，零新增成本              |
   | **L2 在线影子检查** | 每次生成报告后异步（新增） | 新增硬性检查器（structure/narrative/chart\_usage） | 只记录违规到日志/数据库，**不拦截不重试**，收集线上真实违规数据 | <50ms（纯正则/结构比对，无 LLM 调用） |
   | **L3 离线全量评测** | 手动/定期触发（新增）   | 完整评测集 + LLM 评分器 + 排盘回归测试                  | 全面质量评估、回归测试、prompt 优化验证            | 无线上影响                    |

   **为什么这样分层**：

   * **L1 已在跑**：现有 11 个自检函数已集成在主流程，负责拦截+重试，本次不改

   * **L2 影子模式**：新增的硬性检查器以"影子模式"集成到主流程——生成报告后异步跑一次，只记录不拦截。好处是能实时收集线上真实报告的违规数据，补充 badcase 库，且不影响现有重试逻辑和用户体验

   * **L3 离线**：LLM 评分器（叙事性/通顺性/编造检测）成本高、延迟高，只在离线评测时跑。评测集通过 `run_eval.py` 手动或定期触发（CI/CD 或人工）

   **L2 影子检查集成点**（`followup_structured.py`）：

   ```python
   # 在 _normalize_report_data 之后、返回报告之前，异步跑影子检查
   # 不阻塞主流程，不触发重试，只记录违规
   try:
       from app.services.eval.structure_checker import check_structure
       from app.services.eval.narrative_checker import check_narrative
       from app.services.eval.chart_usage_checker import check_chart_usage

       shadow_violations = (
           check_structure(data, user_question)
           + check_narrative(data, is_first_reading=False)
           + check_chart_usage(data, analysis_data)
       )
       if shadow_violations:
           logger.warning(f"[影子检查] 发现 {len(shadow_violations)} 处违规: {shadow_violations}")
           # 可选：写入 shadow_eval_logs 表供后台查看
           await save_shadow_eval_log(person_id, user_question, shadow_violations, data)
   except Exception as e:
       logger.warning(f"[影子检查] 执行失败（不影响主流程）: {e}")
   ```

   **关键原则**：

   * L2 影子检查用 `try/except` 包裹，**任何异常都不影响主流程**

   * L2 只记录不拦截——现有 L1 的 11 个自检函数已覆盖拦截场景，L2 不重复拦截

   * L2 的违规数据可作为 L3 离线评测的输入（哪些违规类型在线上最频繁）

8. **检查器与现有 11 个检测函数的关系**：

   * 现有 11 个检测函数：集成在主流程，**强制重试**

   * 新检查器：独立模块，**只评测告警**，不触发重试

   * 后续可将稳定的新检查器（如结构检查）集成到主流程

## Verification Steps

1. **结构检查器**：对 `test_structured_followup_e2e.py` 生成的报告跑 `check_structure`，验证能检出子问题漏答/block 数量异常/narrative 字数越界
2. **叙事性检查器**：构造含术语的 keyword 和无解释的 narrative，验证能检出
3. **命盘数据使用检查器**：构造含编造大运的报告，验证能检出"编造大运"
4. **排盘正确性**：用 10 个标准命盘跑回归测试，验证已知 bug 被标注
5. **LLM 评分器**：对现有报告跑评分，验证返回合法 JSON
6. **badcase 收集**：触发一次重试终止，验证 badcase 入库
7. **完整评测**：运行 `run_eval.py`，输出 `eval_report.json`，检查各类违规汇总

## 风险点

1. **正则提取命盘实体可能漏匹配**：LLM 叙事化转述后，干支可能不完整（如"甲寅运"写成"甲寅这步运"）。需在正则中放宽匹配，并用 LLM 评分器补充语义判断。

2. **子问题拆解覆盖度估算不准**：`estimate_question_count` 用标点+连词切分，可能误判。初始版本容差 0.8，后续可根据 badcase 调整。

3. **排盘标准答案构造耗时**：手工构造 10 个命盘的标准答案需要用权威工具逐一验证，节气交接日需特别核对年柱。

4. **badcase 入库需要 person\_id**：`generate_followup_structured` 当前无此参数，需修改签名，调用方 `chat.py` 也需同步修改。

5. **LLM 评分随机性**：qwen-flash 评分可能有波动，同一报告多次评分结果不一致。建议评测时取 3 次平均。
