# 积分明细、后台用量记录与订单管理

## 一、需求概述

1. **用户侧前端**：分析历史面板用户头像行最右侧新增箭头入口，点开展示三个功能：
   - 「积分明细」→ 进入积分明细页（充值/消耗记录 + 时间），返回按钮回命理分析首页
   - 「退出登录」（原底部按钮移入菜单）
   - 「用户信息」→ 修改昵称
   - 删除「清空数据」按钮
2. **积分流水增强**：交易记录区分业务类型（首次报告/追问/充值），并提供用户侧查询接口
3. **后台请求用量记录**：每次首次报告与追问落库记录——输入字数、输入token、输出字数、输出token、总token、使用模型、是否成功、用时；仅后台可查看
4. **后台订单记录**：微信支付相关订单持久化并可后台查看；修复支付链路（订单落库 + 支付成功发放积分）。**微信 key 未审批，先保持 mock 充值可用**，key 到位后再正式接入
5. **管理后台**：在现有 admin 面板（admin.shisuansuan.com，nginx BasicAuth）新增「用量记录」「订单记录」页面

## 二、现状分析（调研结论）

- **积分流水已有表**：`transactions`（type=consume/recharge、points、description、created_at），扣费点两处：首次报告在 `person.py:55`（创建人物扣 160）、追问在 `chat.py:177`（扣 40）。**缺陷**：无业务类型字段（只能靠 description 文本区分）、无查询接口、前端仅本地 localStorage 存充值记录
- **支付链路缺陷**：`api/payment.py` 订单存内存字典（重启丢失）；支付成功回调**不发放积分**；DB 版订单能力（`payment_service.create_order/update_order_paid` + `Order` 模型 + alembic 001 已建 orders/transactions 表）已实现但未接线
- **用量仅存日志**：`ai_service.py:435` 与 `followup_structured.py:1888` 有 token 日志，无数据库表、无 user/session 归因
- **后台面板**：admin 子域名 BasicAuth + 前端 `/feedback` 路由（FeedbackDashboard）；后端 feedback 接口无应用层鉴权，纯靠 nginx
- 昵称无修改接口；`/api/user/recharge` 为测试直充（不写流水）

## 三、改动方案

### 改动1：数据库——新增用量表 + 流水业务类型列

**新文件 `backend/app/models/usage_log.py`**：表 `ai_usage_logs`，字段：
`user_id(int)`、`session_id(int, nullable)`、`biz_type(String(20))`（first_reading/followup）、`input_chars(int)`、`input_tokens(int)`、`output_chars(int)`、`output_tokens(int)`、`total_tokens(int)`、`cached_tokens(int)`、`model(String(100))`、`success(Boolean)`、`duration_ms(Integer)`、`created_at`；索引 user_id、created_at

**修改 `backend/app/models/transaction.py`**：新增 `biz_type = mapped_column(String(20), nullable=True)`

**新迁移 `backend/app/alembic/versions/003_add_usage_logs_and_biz_type.py`**（down_revision='91a591685d35'）：
create_table ai_usage_logs + add_column transactions.biz_type（nullable=True）

### 改动2：扣费/充值流水带业务类型

**修改 `backend/app/services/payment_service.py`**：`deduct_points` / `add_points` 增加参数 `biz_type: str | None = None` 并写入 Transaction

**修改 `backend/app/api/person.py:55`**：扣费传 `biz_type="first_reading"`
**修改 `backend/app/api/chat.py:177`**：扣费传 `biz_type="followup"`
**`update_order_paid` 内部充值**：`biz_type="recharge"`

### 改动3：请求用量落库（usage_holder 钩子）

**修改 `backend/app/services/ai_service.py`**：`generate_first_reading_structured` 增加参数 `usage_holder: dict | None = None`，在现有 usage 提取处（L424-438）填充：`input_chars=len(prompt)`、`output_chars=len(raw_content)`、input/output/total/cached tokens、`model`、`success=True`；错误早退路径（L351/457/480）保持 holder 为 success=False。保留现有日志

**修改 `backend/app/services/followup_structured.py`**：`generate_followup_structured` 同样增加 `usage_holder` 参数，在 usage 提取处（L1876-1893）填充同样字段。保留现有日志

**修改 `backend/app/api/chat.py`**：
- `_generate_and_save` 与 `_generate_and_save_first_reading` 增加参数 `user_id: int` 和 `usage_holder`（由 handler 传入 `current_user.id`）
- 任务开始记 `t0=time.time()`；生成结束（成功或异常）后插入 `AiUsageLog`：成功→success=True；异常→success=False（token 字段取 holder 中已有值，缺失记 0），duration_ms=(time.time()-t0)*1000
- 落库用任务自己的 db session，写入失败仅 log 不影响主流程

### 改动4：用户侧接口（积分明细 + 改昵称）

**修改 `backend/app/api/user.py`**：
- `GET /api/user/transactions?limit=100`（需登录）：返回当前用户流水列表（id/type/points/biz_type/description/created_at，时间倒序），复用 `payment_service.get_transactions`（扩展返回 biz_type）
- `PUT /api/user/profile`（需登录）：body `{name}`，校验 1-20 字符，更新 `user.name` 并返回最新 profile

### 改动5：支付链路修复（订单落库 + mock 充值）

**重写 `backend/app/api/payment.py`**（删除内存 `_orders`，改用 DB + 登录鉴权）：
- `POST /create-wechat-order`（需登录）：`payment_service.create_order` 落库（status=pending, pay_method="wechat"）。微信未配置（`settings.WECHAT_APP_ID` 等为空）→ 返回 `{order_id, mock: true}`；已配置→ 走现有 `wechat_pay_service` 真实下单并把 out_trade_no 存入 `trade_no`（为 key 审批后预留，不改 wechat_pay_service 本身）
- `POST /orders/{order_id}/mock-pay`（需登录 + 校验订单属主 + 仅 pending 可支付）：`payment_service.update_order_paid`（status=paid、paid_at、trade_no="MOCK-{ts}"）→ 自动发放积分并写 recharge 流水
- `POST /wechat/callback`：验签后按 out_trade_no 查 DB 订单 → `update_order_paid` 发放积分（真实接入后生效，幂等：已 paid 直接返回 SUCCESS）
- `GET /order-status/{order_id}`：改查 DB
- **删除** `/api/user/recharge` 测试直充接口（前端改用 mock-pay）

**修改 `backend/app/config.py`**（如缺）：确认 WECHAT_APP_ID/MCH_ID 等配置项存在可读

## 四、假设与决策

1. 后台管理接口与现有 feedback 接口同等防护级别（nginx BasicAuth，应用层不加鉴权），保持架构一致
2. 微信支付保持 mock 可用：创建订单→前端模拟支付→mock-pay 发放积分；真实微信下单/回调分支保留，key 审批通过后配置环境变量即启用
3. 删除测试接口 `/api/user/recharge`（新流程 mock-pay 完全替代，且旧接口不写流水）
4. 字数按 Python `len()` 字符数统计；输入字数=system prompt 长度，输出字数=LLM 原始返回长度
5. 失败请求也记录用量（token 缺失记 0），便于排查
6. 积分明细暂不展示变动后余额（表无该字段，避免改表扩大范围）
